# 分层上下文记忆

六个角色共用 `backend/app/agents/memory.py`。Leader 在调用模型前处理消息；Worker 的 LangGraph 使用独立 memory 节点先保存替换后的状态，再进入 agent 节点。工具本身无需接入压缩接口，新增工具的 `ToolMessage` 自动适用。

## 预算与三层处理

预算使用 `AgentSpec.context_window` 或 `QWEN_CONTEXT_WINDOW`（默认 131072），预留 25% 给输出和协议开销，再减去当前工具 schema。调用前用 UTF-8 字节长度估算消息与参数成本；这不是供应商的精确 tokenizer，也不用于计费统计。供应商仍报上下文超限时，额外进行一次干净上下文重试，持续超限不会无限循环。

1. **初级折叠**（`backend/app/agents/context_fold.py`，不调用模型，按“指针”而非删除处理）：
   - **按内容量分层**（以“轮”为单位，一条模型消息加上它的工具结果，从新到旧累计**原文**的估算 token）：
     - 原文层：最新的轮次累计不超过 `WDRUNGE_FOLD_VERBATIM_TOKENS`（默认 30000），保持原文；当前轮次（含尚未被模型读到的结果）始终原样。
     - 摘录层：再往前累计不超过 `WDRUNGE_FOLD_EXCERPT_TOKENS`（默认 15000），保留按工具摘要和正文开头 600 字符，并注明“共 N 字符，用 recall_context 或按偏移重读”。
     - 指针层：更早的结果只剩一行指针（工具名、路径/文档/章节/偏移、大小、状态、错误摘要、消息 ID）。
     - 上下文窗口较小时，两层分别不超过预算的 1/3 和 1/6。
     - 轮次不可拆，实际原文量约 24K～30K。估算 token = UTF-8 字节/2：中文约 1.5/字，代码约 0.5/字符。30K 约等于 2 万中文字或 6 万字符代码，足以同时容纳“写一个样式表所需的设计令牌和组件章节”或“写路由层所需的各模块签名”。Blog2 只保留最近 3 轮，3 轮装不下实现任务的工作集，于是出现“读 → 被折叠 → 再读”的循环。
     - 原文的事实（层级、原始字符数和估算 token、是否整读）在首次折叠时记入 `additional_kwargs['fold']`，这个字段不会发给模型。层级只升不降，重复折叠结果不变。
   - **被取代的结果**：同一文件、文档章节、目录、检索、进程状态或相同前台命令被再次读取/执行后，旧结果替换为一行存根，指向新结果的消息 ID；完整读取取代该文件的所有分段读取，“是否完整”依据首次折叠时记录的原文事实判断（Blog2 曾在已折叠的文本上判断，`offset=0` 的分段读取被误认为整读，后端一轮误删 41 条结果）；`write_project_file` 成功后，该文件此前的读取标为“已过期”。当前轮次除外。
   - **按工具摘要**：更早的结果超过 600 字符时，按工具保留决策所需事实而非截取开头：命令保留 argv、退出码、错误/警告行和末尾几行；`browser_verify` 保留 passed、断言结果、错误样例和截图路径；`read_project_file` 保留路径、sha256、行数和下一页 offset；协作文档保留文档/版本/章节标题，**每份文档最新的一份大纲（发布回执或大纲读取）保留全部章节 ID**，作者不必在每次编辑前重读大纲；`read_project_file` 另保留文件结构（带行号的类/函数/导出声明，Markdown 为标题，最多 1500 字符）；其他 JSON 保留结构化缩略；无法识别的文本才截取开头。写入文件的正文参数替换为长度、sha256 前缀和同样的文件结构（文件在磁盘上）。其他调用参数在摘录层只保留长字符串的前 120 字符；单个调用仍超过 1500 字符（例如带十几处编辑的文档发布），或已到指针层时，长字符串只剩占位，保留字段结构（文档 ID、版本、摘要、章节 ID）。Blog1 运行中，作者回读自己的文档 98 次、后端回读自己的代码 19 次，原因就是这些信息被折叠掉了。
   - **任务台账**：在折叠边界插入一条台账消息（`additional_kwargs.context_ledger`），记录已写/已读文件及哈希、共享文档版本、后台进程与端口、已执行命令的最近退出码、浏览器验证结果、尚未解决的工具失败（之后同一目标成功即移除）。内容不变时复用同一消息，不破坏缓存。
   - **折叠的调用参数不能当值回传**：写文件的正文、过长的参数折叠后留在历史调用里，形式与真实参数相同，模型可能照抄进新调用。占位符带有“不是原值”的说明，Leader 和成员执行任何工具前都会检查参数，发现折叠占位符即拒绝（`folded_placeholder`），不会写进文件或文档。
   - **找回原文**：每个折叠标记和存根都给出消息 ID，`recall_context(message_id, offset, limit)` 从压缩审计中返回该消息的原始内容（限本线程作用域），代替重新执行工具或重读未变的文件。
   - **缓存友好**：只有可回收的估算 token 达到 `WDRUNGE_FOLD_TRIGGER_TOKENS`（默认 12000）或超出预算时才成批折叠，一次折叠到原文层之前，减少改写历史前缀导致的提示缓存失效。

专业成员只绑定常用协作工具；订阅、检索、差异、历史、排期、依赖、快照、决策、维护、交接和 `create_task` 需先调用 `enable_tools` 启用，之后才出现在模型的工具列表中（执行层始终可调用）。Leader 仍绑定全部协作工具。用量记录保存供应商返回的缓存命中 token，工作日志在“累计使用”下显示缓存命中率（仅统计返回了缓存数据的调用）。
2. **历史摘要**：折叠后仍超预算时，使用当前历史作为摘要来源，将每项工具结果限制到 3000 字符（含截断标记），剔除运行时标记 `reissuable_reminder` 的提醒。最近一条任务/用户输入及原文层的轮次保持原文；其之前的历史与其之后、原文层之前的工作分别摘要（摘要放在该输入之前/之后）。台账原样保留并提供给摘要模型以免重复；摘要按“目标与约束、决策、文件与产物、验证证据、未解决错误、下一步”组织。用户自行输入类似 reminder 的文字不会被误删。
3. **干净上下文接续**：当前工作轮次仍过大时，对整个工作状态生成交接，仅保留系统指令、台账和交接摘要。任务身份、权限、工作区和协作状态不变。`checkpoint_context` 同样保留台账。

摘要输入先分块再归并，单个超大用户消息或工具参数同样会切块，摘要调用没有工具权限。摘要的 token 用量计入角色累计用量。

**摘要模型与失败处理**：摘要使用 `WDRUNGE_MODEL_SUMMARY`（`.env` 中为 `qwen3.7-plus`），默认关闭思考（`enable_thinking=false`；`WDRUNGE_SUMMARY_THINKING=1` 可打开），输出上限为 `字数目标×2 + 4096`。推理 token 也计入 `max_tokens`：Blog2 两次摘要都正好输出 12,000 token、`finish_reason=length`，没有可用文本，任务因此失败。现在被截断或为空的摘要会用一半的字数目标重试一次；仍然失败（包括接口报错、无法收敛）时改用**平台交接**，不调用模型，也不让任务失败：

| 部分 | 内容 |
| --- | --- |
| 系统提示词、任务台账 | 原样 |
| 任务输入 | 项目交接、任务消息（Assigned task + handoff）、之前的摘要，原样；单条超过 6000 字符时截断并给出 `recall_context` 指针 |
| 交接说明 | 原因；本任务 journal 最近 12 条笔记；被替换历史中自己最近 8 段文字（计划和决定）；最近 15 次工具调用（名称、精简参数、成功/失败、结果消息 ID）；如何找回旧结果 |
| 最近原文 | 原文层的轮次，从完整的模型轮次开始；超预算时从最旧的轮次开始丢弃 |

只有系统提示词加工具 schema 本身就超过预算时，才抛出 `ContextBudgetError`。

**只读循环**（`backend/app/agents/progress.py`）：如果一轮里的工具调用全部是读取或查看（读文件、读文档、检索、目录、找回、查看类协作工具、进程日志，以及只由 cat/sed -n/grep/ls 等读工具组成的命令，含 `sh -c` 包装），就算只读轮。写文件、发布、交付、构建/测试/启动服务、浏览器验证都算推进。worker 连续只读 `WDRUNGE_READ_STREAK`（默认 12）轮时注入一次提醒；到 2 倍时自动换成平台交接（保留最近原文）并再提醒一次；之后每满 N 轮重复。提醒消息记录当时的计数，所以计数能跨过交接继续累计。worker 提示词同时要求“边读边写”。

## 主动选择上下文

所有角色都可单独调用 `checkpoint_context`，提供结构化交接后在干净上下文继续当前工作。混合调用其他工具时会返回错误，防止重置破坏尚未处理的工具调用。

执行中因运行时异常（模型接口、上下文管理、平台）失败的任务被标记为可续接：Leader 重试时恢复原线程，原线程的上下文继续由分层压缩管理，不再全新冷启动。续接的那次尝试如果又因非瞬时错误失败，下一次重试改为 `fresh`，避免反复回放有问题的上下文。Leader 重试（transition 到 queued）的结果里有 `next_attempt` 字段，写明下一次是续接还是全新上下文。以 `fresh` 启动时，上一轮线程的台账（写过的文件、验证结果、进程、未解决失败）会追加到新一轮的 handoff，避免重做已完成的工作；上一轮的进程已在结束时停止。

委派仍支持 `fresh`、`continue`、`auto`：`fresh` 为新任务提供自足 handoff；`continue` 接续已有会话；`auto` 接续已有会话并交由分层压缩管理，不再达到 60% 就直接丢弃旧上下文。上下文清理不会隐式提交、完成、取消或新建任务。后台调度的任务生命周期继续由原调度器管理。

压缩使文件正文离开上下文时，会更新文档读取上下文 ID，允许重新读取相同修订；不会把未处理的 inbox 提醒自动确认已读。

## 持久化与可追溯性

- `context_compactions` 保存角色、作用域、压缩阶段、原消息 ID 区间、源消息、替换消息和压缩前后估算长度。折叠记录只保存被替换、移除或新增的消息；某消息首次出现的记录即其原文，供 `recall_context` 查找。原聊天记录不修改。
- `context_memory` 保存 Leader 的模型历史视图与外部聊天历史截止位置。重启后加载压缩视图，再追加截止点之后的消息。
- Worker 使用 LangGraph 持久检查点保存替换后的消息列表。替换使用 `RemoveMessage(REMOVE_ALL_MESSAGES)`，避免旧历史被消息 reducer 重新追加。
- `agent_usage` 按成功取得的供应商 usage 记录每次六个角色模型调用（含摘要）的真实累计 token。启动时聚合恢复；后台临时实例只贡献自身新增用量，避免重复加载角色历史总量。
- migration `0004_context_memory` 和启动时 `metadata.create_all` 均支持旧数据库添加新表。用户执行“清除所有记录”时同步清空。

历史版本未记录的用量无法可靠倒推。未收到供应商 usage 的请求不伪造计费数；标题模型及工具审核模型不在六角色统计口径内（审核模型以 `reviewer` / `review` 单独记账）。所有模型都开启 `stream_usage`，审核调用使用非流式：在流式执行的图里，`ainvoke` 也会转成流式，不开启 include_usage 时供应商不返回用量，Blog2 的 85 次审核因此全部漏记。`agent_usage.reasoning_tokens` 记录输出 token 中用于推理的部分（`output_token_details.reasoning`），会话用量接口按角色、用途、任务、模型汇总。工具调用抛出异常（参数校验失败、not_found 等）时，`tool_calls` 记录规范化后的失败结果。

## 回归覆盖

`tests/test_context_tiers.py` 覆盖按内容量分层、小窗口、已折叠的分段读取不再取代其他区段、发布参数折叠、摘要截断后重试再转平台交接、摘要关闭思考、只读判定、worker 的提醒与交接、提醒确认。`tests/test_context_layers.py` 覆盖折叠占位符被拒绝、最新大纲保留全部章节 ID、写入与读取的文件结构、当前轮次不折叠、取代存根、按工具摘要、台账、成批折叠与只记录变更、原文找回、摘要保留任务输入与近期轮次、干净接续与检查点保留台账、重试交接。`tests/test_context_memory.py` 覆盖初级折叠、3000 字符限制、reminder 区分、摘要分块、干净上下文接续、主动检查点、摘要失败转平台交接、供应商超限重试、持久化恢复与并发实例用量。测试使用本地假模型，不发送付费请求。
