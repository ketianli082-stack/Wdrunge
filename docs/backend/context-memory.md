# 分层上下文记忆

六个角色共用 `backend/app/agents/memory.py`。Leader 在调用模型前处理消息；Worker 的 LangGraph 使用独立 memory 节点先保存替换后的状态，再进入 agent 节点。工具本身无需接入压缩接口，新增工具的 `ToolMessage` 自动适用。

上下文由三块组成（设计依据见 `docs/reports/2026-10-06-context-desk-design.md`）：

| 块 | 内容 | 位置 |
| --- | --- | --- |
| **工作台（desk）** | 读过的文件和文档章节，各一份，**当前内容**；读工作台上已有的东西只返回一行通知 | 原文层边界，紧跟台账 |
| **状态** | 台账（文件、文档版本、进程、检查、未解决失败、代码索引）+ 有上限的工作段摘要 | 台账在边界；段摘要在原位 |
| **近期记录** | 最近几轮原文（命令、浏览器、检索、模型正文）；更早的折叠成摘要、指针、存根 | 边界之后 |

所有阈值按**实际（计费）token** 配置；估算（UTF-8 字节 / 2）用每次调用返回的 `prompt_tokens` 按线程校准（`context_meter.py`，比值记在回复的 `response_metadata.wdrunge_token_ratio`，夹在 0.4～1.2）。Blog4 实测 1 估算 token ≈ 0.64 实际 token。

## 预算与压缩流水线

预算是 `WDRUNGE_CONTEXT_TOKENS`（默认 56000 实际 token），不超过窗口（`AgentSpec.context_window` 或 `QWEN_CONTEXT_WINDOW`，默认 131072）的 75%，再减去当前工具 schema。预算越大每次调用越贵，默认值取校准之前流水线实际运行的水平。估算值不是供应商的精确 tokenizer，也不用于计费统计。供应商仍报上下文超限时，额外进行一次干净上下文重试，持续超限不会无限循环。

每次调用模型前，历史按下面的顺序处理。前一层不够时才用下一层，能不调模型就不调模型。设计依据见 `docs/reports/2026-10-05-context-compression-strategy.md`。

| 层 | 做什么 | 调模型 | 代码 |
| --- | --- | --- | --- |
| L0 入口预算 | 刚返回、模型还没看到的结果：单条封顶、单次响应合计封顶、未变内容去重 | 否 | `context_fold.ingest` |
| L1 历史剪除 | 冗余结果换成存根；原文层之外，整次都冗余的响应连同调用一起删除 | 否 | `context_fold.supersession` / `prune` |
| L2 微压缩 | 可重新获取的工具结果按层折叠为摘录、指针；**资源读取（desk 策略）移入工作台**，只留一行指针 | 否 | `context_fold.fold`、`context_desk` |
| L3 工作段摘要 | 原文层之外已完成的工作段换成一段短摘要；合计超过 `WDRUNGE_SEGMENT_TOKENS` 时最旧的几段合并 | 是（单段小调用） | `ContextMemory.collapse` / `merge_summaries` |
| L4 整体压缩 | 整段历史摘要；不可用时平台交接 | 是 | `ContextMemory.summarize_history` |

### 什么时候改写历史

改写历史中的任何一条，供应商的前缀缓存从这条往后就全部失效（DashScope 没有 Claude 的 `cache_edits`）。所以 L1～L3 的改动合并成**一次**提交，并按“租还是买”规则决定什么时候提交（`ContextMemory.worth_rewriting`）：

- **两边的代价**：
  - 上一次请求发出的前缀（最新一次回复之前的全部消息）已被缓存，命中价约为全价的 `WDRUNGE_CACHE_HIT_PRICE`（默认 0.2）。
  - 不改写：每次调用都为本可折叠的 R 个 token 多付 p·R。
  - 改写：下一次请求要按全价重发第一处改动之后的内容 S，代价 (1−p)·S。
- **提交时机**：等待累计多付的钱达到一次改写的代价时才改写。等待让 R 变大，一次大改写代替多次小改写。这是标准的 rent-or-buy 规则，最坏情况下花费不超过事后最优安排的两倍。
- **不受规则约束、直接改写的情况**：
  - **缓存已失效**：距上一次请求超过 `WDRUNGE_CACHE_COLD_SECONDS`（默认 600 秒）。实测 DashScope 隐式缓存约 10 分钟内有效，超过后约一半调用完全不命中。每次响应的 `response_metadata.wdrunge_requested_at` 记录请求时间。此时改写没有代价，能省 `WDRUNGE_FOLD_COLD_MINIMUM`（默认 2000）以上就改。
  - **只改了还没发出的消息**：没有代价。
  - **超过预算**：必须改写。
  - **超过预算 80%，且这一次改写能降到 60% 以下**：现在就改，避免长任务一直贴着上限工作。降不到 60% 时不强制，否则每次调用都会改一点、每次都让缓存失效。
- **为什么不按命中率判断**：上一次命中率低，通常只说明上一次刚改写过；那次调用已经建好新缓存，下一次照样命中。

用 Blog2 三个成员的真实线程重放（`agent_usage` 加 `tool_calls`，优先取审计里的完整原件），与旧做法的近似（所有工具都可折叠、没有入口预算/剪除/段摘要、固定 12K 批量）对比，按缓存计价的输入成本：后端 −16%，前端 −24%，美工 −11%；未命中缓存的 token 分别从 1.77M 降到 1.01M、1.97M 降到 1.09M、0.46M 降到 0.34M；平均上下文分别从 73K 降到 70K、75K 降到 67K、65K 降到 61K。

### L0 入口预算

在压缩流水线的第一步统一处理（Worker 与 Leader 共用），不在每个工具里各写一套。

- **单条上限**：`WDRUNGE_RESULT_TOKENS`，默认 8000 估算 token。
- **单次响应合计**：`WDRUNGE_RESPONSE_RESULT_TOKENS`，默认 20000。“单次响应”指模型的一次回复加上它发起的工具调用的结果，不是整个任务。超出时先削最大的结果。
- **小窗口**：上下文窗口较小时，两者分别不超过预算的 1/4 和 1/3。
- **超出时怎么截**：
  - 有 `offset` 参数的工具（可分页的读取）保留开头，注明从哪个 offset 继续；
  - 其他输出保留开头约 60%、结尾约 40%；
  - JSON 结果保留结构，只截最长的字符串字段。
- **找回**：原件进压缩审计，`recall_context(message_id, offset)` 可取回。
- **Blog2 实测**：单条结果 p99 为 8.9K，超过 8K 的只有 1.2%（主要是文档读取和 recall，都可分页）；单次响应合计最大 16.6K，从未超过 20K。
- **命中工作台**：desk 策略的读取（`read_project_file`、`collaboration_read`），其结果已经由工作台上的某个条目显示（同一份，或整读条目覆盖的区间 / 章节，内容一致）时，返回一行 `{"on_desk": true, "entry": …}` 通知。源变了（自己刚写过、文档刚发布）就正常返回全文；`force=true` 照常返回。
- **未变内容去重**：
  - **何时回通知**：可重新获取的工具，用完全相同的参数再次调用，结果与上一次逐字相同，并且上一份在上下文里**仍是原文**时，返回一条 `unchanged` 通知，不再重发全文。
  - **怎么拿到全文**：紧接着再调用一次（或传 `force=true`）会返回全文。
  - **原件保留**：被通知引用的原文在通知仍处于原文层时保持原样，不会被折叠或并入段摘要。
- **替换旧机制**：去重取代了原来 `collaboration_read` 服务端的 `already_in_context` 回执。旧机制在每次压缩时重置整个线程的回执，Blog2 折叠了 86 次，所以一次都没生效。

### L1 历史剪除（只删冗余）

**冗余的判定**：删掉之后，模型能从剩下的内容得到同样的信息。以下结果在当前轮次之外换成一行存根，指向更新的那份：

- 同一调用（工具加参数完全相同）后来返回了逐字相同的结果；
- 同一调用失败后，后来成功了；
- 同一目标（文件、文档章节、目录、检索、进程状态、相同前台命令）有更新的结果；完整读取取代该文件的所有分段读取。

读过的文件后来被自己改写时，旧读取**不再**标为“已过期”：它移入工作台，工作台显示文件的当前内容。

**整次删除**：原文层之外，一次响应的结果全是存根或通知、且模型这次回复没有正文时，连同调用一起删除（不拆开调用和结果）。

**其他删除**：被新目标提醒取代的旧目标提醒，以及已结束的只读连续计数提示，也会删除。

**不删的**：
- 同一文件的不同区间；
- 换了参数或做法才成功的失败（失败原因解释了为什么换做法）；
- 未解决的失败；
- 模型的正文；
- 收件箱提醒（同事的消息）；
- 原文层里的内容。

删除的原件进审计，按消息 ID 可找回。

### L2 微压缩（按工具声明）

- **声明方式**：工具用 `@tool(context_policy=RECOMPUTABLE)` 声明结果可重新获取（`app/agents/context_policy.py`），没有声明的默认 `durable`，新工具不会被误压。
- **可重新获取**：读文件、目录、检索、外部文件、项目文件列表、环境检测、命令与进程、项目检查、服务检查、浏览器验证、recall，以及协作工具中的读取/查看类动作。
- **durable**：写文件、发布、流转、发消息、记日志、登记服务等。这类结果不会被机械截断，只由 L3 段摘要或 L4 替换。
- **声明 `desk`**：资源读取（文件区间、文档章节 / 大纲）。它们不进摘录层：原文层之外直接变成一行指针（注明“on the desk”），内容移入工作台（见下一节）。
- **分层**：按**单条消息**（不是整轮）从新到旧累计原件的估算 token。每条最多按单条上限计入，旧的超大结果不会把更早的历史整体挤成指针。
  - 原文层：最新的结果累计不超过 `WDRUNGE_FOLD_VERBATIM_TOKENS`（默认 8000 实际 token），保持原文；当前轮次始终原样。读取搬到工作台之后，这一层只放命令、浏览器、检索结果和模型正文。
  - 摘录层：再往前 `WDRUNGE_FOLD_EXCERPT_TOKENS`（默认 15000），保留按工具摘要和正文开头 600 字符，并注明“共 N 字符，用 recall_context 或按偏移重读”。
  - 指针层：更早的结果只剩一行指针（工具名、路径/文档/章节/偏移、大小、状态、错误摘要、消息 ID）。
  - 上下文窗口较小时，两层分别不超过预算的 1/3 和 1/6。
  - 阈值是实际 token；按线程校准比换算成估算单位再比较。
  - 原文的事实（层级、字符数、估算 token、内容摘要哈希、是否整读）在进入上下文或首次折叠时记入 `additional_kwargs['fold']`，这个字段不会发给模型。层级只升不降，重复折叠结果不变。
- **按工具摘要**：更早的结果超过 600 字符时，按工具保留决策所需的事实，而不是截取开头：
  - 命令：argv、退出码、错误/警告行、末尾几行。
  - `browser_verify`：passed、断言结果、错误样例、截图路径。
  - `read_project_file`：路径、sha256、行数、下一页 offset，以及文件结构（带行号的类/函数/导出声明，Markdown 为标题，最多 1500 字符）。
  - 协作文档：文档、版本、章节标题。每份文档最新的一份大纲（发布回执或大纲读取）保留全部章节 ID。
- **调用参数**：
  - 写入文件的正文换成长度、sha256 前缀和文件结构。
  - 其他长参数在摘录层只保留前 120 字符。
  - 到指针层，或单个调用仍超过 1500 字符时，只剩占位，保留字段结构。
  - 折叠占位符不能当值回传：执行任何工具前都会检查，发现即拒绝（`folded_placeholder`）。
- **任务台账**：在原文层边界插入一条台账消息（`additional_kwargs.context_ledger`），记录：
  - 已写/已读文件及哈希；
  - 共享文档版本；
  - 后台进程与端口；
  - 已执行命令的最近退出码；
  - 浏览器验证结果；
  - 尚未解决的工具失败；
  - **代码索引**：自己写过或整读过的代码文件里的声明（函数/类签名、导出、CSS 选择器、Markdown 标题，带行号），最近写过的在前，合计不超过 `WDRUNGE_CODE_INDEX_CHARS`（默认 6000 字符），单个文件最多 1500 字符。写文件的参数会被折叠掉；没有这份索引时，agent 只能回读自己的代码来确认一个名字或类名（Blog3 前端把 `pages.css` 读了 66 次）。

  内容不变时复用同一条消息。`write_project_file` 的回执带上写完后整个文件的结构（`Structure: ...`）；同一文件再次写入后，旧回执里的结构被替换成一行说明，回执本身保留。
- **找回原文**：每个折叠标记、存根和摘要都给出消息 ID，`recall_context(message_id, offset, limit)` 从压缩审计返回原始内容（限本线程）。

### 工作台（`context_desk.py`）

- **条目**：一次成功的读取调用（工具名 + 参数）及其最新结果。键：文件 `(path, offset, limit)`；文档 `(document_id, section_id | whole | outline, offset)`。检索、目录、命令、浏览器结果不进工作台，它们是观察而不是资源。
- **准入**：读取结果先以原文进入近期记录；下一次改写历史时，原文层之外的读取移入工作台，记录里只留一行指针。不需要模型做任何事。
- **覆盖**：整读覆盖同一文件的所有区间，整篇文档覆盖它的所有章节和大纲；被覆盖的条目合并掉。工作台上有某文档的条目时，始终附带该文档的**最新大纲**（章节 ID 和标题）。
- **刷新**：每次改写历史时，每个条目**重新执行同一个读取**（通过 agent 自己的工具集，文档读取去掉 `version` 取最新）：内容变了就替换并标注“updated since you read it”；读取失败（文件删除、章节不存在）的条目删除，并在工作台末尾列出。区间条目按同样的偏移重读，标题写明是当前文件的哪一段。
- **命中**：读工作台已显示的内容，入口返回一行通知（见 L0）。通知折叠后成为存根，整轮只有通知时连同调用一起删除；每次命中都计入条目热度。
- **淘汰**：超过 `WDRUNGE_DESK_TOKENS`（默认 20000 实际 token，且不超过预算的 35%）时按热度淘汰最冷的：`heat = Σ 0.5^((当前轮 − 读取轮) / WDRUNGE_DESK_HALF_LIFE)`（默认 40 轮）。被淘汰又读回来的条目继承之前的读取次数，排在只读过一次的条目后面。淘汰的条目在工作台末尾列出（最多 20 个），需要时再读。
- **渲染**：一条 `HumanMessage`（`additional_kwargs.context_desk` 存结构化条目），条目按键排序；文件原文不加行号，和 `read_project_file` 返回的一致，便于 `edits` 的 `old_text` 匹配。内容没变时复用同一条消息（ID 和正文），只更新簿记。
- **缓存**：工作台只在改写历史时变化，不单独触发改写；它的大小计入 rent-or-buy 的 S。
- **交接**：`checkpoint_context`、平台交接和 L4 摘要都保留工作台（放不下时先放弃工作台，再裁输入）；全新尝试的 handoff 列出上一次尝试工作台上的条目名。
- **为什么不是“多留一会儿”**：Blog4 报告 10.1 节的模拟说明按时间延长保留是净增 token。工作台不是延长保留，而是把“最近读的”换成“正在用的”，去重并随源刷新；读取搬出原文层后，原文层相应缩小，每次调用的大小和之前持平。

### L3 工作段摘要

- **怎么切段**：按里程碑切。一次成功的 durable 调用（写文件、发布、流转、发消息、记日志……）结束一段。任务/用户输入、已有摘要和台账不会被跨越。
- **可折叠的段**：
  - 整段在原文层之外；
  - 至少 1500 估算 token，最多 24000；
  - 段内没有某文档最新的大纲，也没有被 `unchanged` 通知引用的原文。
  - 未解决的失败不阻止折叠：台账原样列出它们和对应消息 ID。
- **摘要内容**：用摘要模型（关闭思考）写 3～10 行，记录“现在知道什么”而不是“做了什么”：确认过、之后要用的名称、签名、字段、路由、类名、配置值（尽量带 file:line），决定及原因，改了哪些文件/文档和 ID，放弃的做法及原因，中途停下时的下一步。不写只有“读了 X”而没有事实的行；台账（含代码索引）里已有的不重复。Blog3 的段摘要多是“Read router, api… No files modified”，段被摘要掉后同样的读取只能重做。真实调用一次，一段 7 轮、输入 8.7K token：输出 120 token，用时 4.9 秒。
- **摘要消息**：消息 ID 由段的首尾消息决定，同一段每次得到同一条消息，不会无谓地破坏缓存。
- **上限**：所有段摘要合计超过 `WDRUNGE_SEGMENT_TOKENS`（默认 4000 实际 token）时，最旧的若干段（合计不少于上限的一半）用摘要模型合并成一条，在后台生成、随下一次改写提交（Blog4 后台线程 24 段占上下文 21%）。
- **时机**：
  - 剪除和微压缩之后超过预算 60% 时，在**后台**为可折叠的段生成摘要，不阻塞当前调用；
  - 已生成的摘要随下一次改写一起提交；
  - 超过 80% 时，未完成的摘要最多等待 120 秒；
  - 生成失败的段留给 L4。

### L4 整体压缩

剪除、微压缩和段摘要之后仍超预算（或供应商报超限、模型主动 checkpoint）时：

- **保留**：最近一条任务/用户输入和原文层的轮次保持原文，**原文层不截断**。
- **摘要**：该输入之前的历史，以及它之后、原文层之前的工作，分别摘要（放在该输入之前/之后）。
  - 只有要摘要的部分，每项工具结果截到 3000 字符；
  - 剔除运行时标记 `reissuable_reminder` 的提醒；
  - 已有的段摘要直接作为输入。
- **台账**：原样保留，并提供给摘要模型以免重复。摘要按“目标与约束、决策、文件与产物、确认的事实、验证证据、未解决错误、下一步”组织。
- **当前轮次仍过大时**：对整个工作状态生成交接，只保留系统指令、台账和交接摘要。`checkpoint_context` 同样保留台账。

专业成员只绑定常用协作工具；订阅、检索、差异、历史、排期、依赖、快照、决策、维护、交接和 `create_task` 需先调用 `enable_tools` 启用，之后才出现在模型的工具列表中（执行层始终可调用）。Leader 仍绑定全部协作工具。用量记录保存供应商返回的缓存命中 token，工作日志在“累计使用”下显示缓存命中率（仅统计返回了缓存数据的调用）。

摘要输入先分块再归并，单个超大用户消息或工具参数同样会切块，摘要调用没有工具权限。摘要的 token 用量计入角色累计用量。

**摘要模型与失败处理**：摘要使用 `WDRUNGE_MODEL_SUMMARY`（`.env` 中为 `qwen3.7-plus`），默认关闭思考（`enable_thinking=false`；`WDRUNGE_SUMMARY_THINKING=1` 可打开），输出上限为 `字数目标×2 + 4096`。推理 token 也计入 `max_tokens`：Blog2 两次摘要都正好输出 12,000 token、`finish_reason=length`，没有可用文本，任务因此失败。现在被截断或为空的摘要会用一半的字数目标重试一次；仍然失败（包括接口报错、无法收敛）时改用**平台交接**，不调用模型，也不让任务失败：

| 部分 | 内容 |
| --- | --- |
| 系统提示词、任务台账 | 原样 |
| 任务输入 | 项目交接、任务消息（Assigned task + handoff）、之前的摘要，原样；单条超过 6000 字符时截断并给出 `recall_context` 指针 |
| 交接说明 | 原因；本任务 journal 最近 12 条笔记；被替换历史中自己最近 8 段文字（计划和决定）；最近 15 次工具调用（名称、精简参数、成功/失败、结果消息 ID）；如何找回旧结果 |
| 最近原文 | 原文层的轮次，从完整的模型轮次开始；超预算时从最旧的轮次开始丢弃 |

只有系统提示词加工具 schema 本身就超过预算时，才抛出 `ContextBudgetError`。

**只读循环**（`backend/app/agents/progress.py`）：
- **判定**：一轮里的工具调用全部是读取或查看（读文件、读文档、检索、目录、找回、查看类协作工具、进程日志，以及只由读工具组成的 shell 命令），就算只读轮。shell 命令按词法解析：`cd`、`for … do … done`、`if … then … fi`、`2>&1`、`>/dev/null` 和引号里的 `>`（如 `awk 'NR>=460'`）都不影响判定；写到文件的重定向、`tee`、`sed -i`、`perl -pi`、`$(…)` 不算只读。写文件、发布、交付、构建/测试/启动服务、浏览器验证、journal 记录都算推进。
  - Blog3 之前的判定把 `cd src && grep …` 这类命令当成推进，前端最长 178 轮的只读循环从没触发过处理。
- **处理**：连续只读 `WDRUNGE_READ_STREAK`（默认 12）轮时提醒一次。到 2 倍时**暂停读取**：之后只读的调用直接返回 `reads_paused` 错误（不执行），直到 agent 写入、运行或用 `collaboration_journal(kind="next")` 写下下一步；任何一次推进都会解除暂停。上下文不清空，工具列表不变（不破坏缓存）。
  - 以前到 2 倍时会换成干净交接。但读个不停通常是因为工作集装不下，交接把刚读进来的又扔掉，下一轮只能再读。
- 提醒消息记录当时的计数，计数能跨过折叠继续累计。worker 提示词同时要求“边读边写”。

## 主动选择上下文

所有角色都可单独调用 `checkpoint_context`，提供结构化交接后在干净上下文继续当前工作。混合调用其他工具时会返回错误，防止重置破坏尚未处理的工具调用。

执行中因运行时异常（模型接口、上下文管理、平台）失败的任务被标记为可续接：Leader 重试时恢复原线程，原线程的上下文继续由分层压缩管理，不再全新冷启动。续接的那次尝试如果又因非瞬时错误失败，下一次重试改为 `fresh`，避免反复回放有问题的上下文。Leader 重试（transition 到 queued）的结果里有 `next_attempt` 字段，写明下一次是续接还是全新上下文。以 `fresh` 启动时，上一轮线程的台账（写过的文件、验证结果、进程、未解决失败）会追加到新一轮的 handoff，避免重做已完成的工作；上一轮的进程已在结束时停止。

委派仍支持 `fresh`、`continue`、`auto`：`fresh` 为新任务提供自足 handoff；`continue` 接续已有会话；`auto` 接续已有会话并交由分层压缩管理，不再达到 60% 就直接丢弃旧上下文。上下文清理不会隐式提交、完成、取消或新建任务。后台调度的任务生命周期继续由原调度器管理。

压缩不会把未处理的 inbox 提醒自动确认已读。

## 持久化与可追溯性

- `context_compactions` 保存角色、作用域、压缩阶段、原消息 ID 区间、源消息、替换消息和压缩前后估算长度。折叠记录只保存被替换、移除或新增的消息；某消息首次出现的记录即其原文，供 `recall_context` 查找。原聊天记录不修改。
- `context_memory` 保存 Leader 的模型历史视图与外部聊天历史截止位置。重启后加载压缩视图，再追加截止点之后的消息。
- Worker 使用 LangGraph 持久检查点保存替换后的消息列表。替换使用 `RemoveMessage(REMOVE_ALL_MESSAGES)`，避免旧历史被消息 reducer 重新追加。
- `agent_usage` 按成功取得的供应商 usage 记录每次六个角色模型调用（含摘要）的真实累计 token。启动时聚合恢复；后台临时实例只贡献自身新增用量，避免重复加载角色历史总量。
- migration `0004_context_memory` 和启动时 `metadata.create_all` 均支持旧数据库添加新表。用户执行“清除所有记录”时同步清空。

历史版本未记录的用量无法可靠倒推。未收到供应商 usage 的请求不伪造计费数；标题模型及工具审核模型不在六角色统计口径内（审核模型以 `reviewer` / `review` 单独记账）。所有模型都开启 `stream_usage`，审核调用使用非流式：在流式执行的图里，`ainvoke` 也会转成流式，不开启 include_usage 时供应商不返回用量，Blog2 的 85 次审核因此全部漏记。`agent_usage.reasoning_tokens` 记录输出 token 中用于推理的部分（`output_token_details.reasoning`），会话用量接口按角色、用途、任务、模型汇总。工具调用抛出异常（参数校验失败、not_found 等）时，`tool_calls` 记录规范化后的失败结果。
