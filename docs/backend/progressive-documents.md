# 整篇读取与渐进式文档

## 整篇读取

`collaboration_read(document_id, whole=true)` 一次返回文档全文（按 offset/limit 分页，分页尽量落在完整的 Markdown 块边界）以及章节大纲（ID、标题、层级，仅首页返回），之后仍可按章节 ID 编辑。用于从头到尾读一份文档，代替“先读大纲、再逐节读取”的多次调用（运行记录中后端读契约用了 26 次分节调用）。

## 带子章节读取

`collaboration_read` 的 `document_id` 也接受文档路径（模型常常只记得路径）；找不到时报错里列出已有的文档及其 ID。

`collaboration_read(document_id, section_id, subtree=true)` 返回该章节连同全部子章节的正文，并列出其中的章节（`sections`）。不带 `subtree` 时，父章节只返回自己的直接正文。需求文档按“一级标题 = 模块”组织，读一个模块因此是一次调用；Blog5 的 108 次文档读取里有 78 次是逐章节读取。工作台把带子章节的读取记成一个条目，之后读其中任一子章节会得到“已在工作台上”的通知。

## 交付文档草稿

任务声明了 `documents` 时，首次执行（非续跑）开始前，平台为尚不存在的文档发布一份分章节草稿，作者为该任务负责人：

- 按路径里的完整单词判断文档类型：报告/验证/测试、契约/接口、需求、设计/主题、其他（按子串匹配时，requirements 里的 “ui” 曾让需求文档被当成设计文档）；按任务目标文本的语言生成中文或英文章节；
- 需求、设计、报告三类草稿本身就是结构示例，只有占位符（尖括号里的说明），没有示例内容：需求草稿是两个模块，每个模块有“需求N”和“验收标准”；设计草稿是“气质 / 色调倾向 / 素材清单”三节；报告草稿是每个模块一张“检查项 / 预期 / 实际 / 结论 / 证据”的表。契约和其他文档仍是固定章节加“（待填写）”。占位符没有替换完的文档视为未写完；
- 记录为 `draft`（文档 ID → 任务、草稿版本）；
- 负责人的 handoff 说明草稿位置和文档 ID，要求每完成一部分就用 `collaboration_publish` 的 `replace_section_body` 填写对应章节；草稿的章节结构不合适时，可在草稿未被填写前用 `changes=[{document_id, base_version, summary, content}]` 一次整体替换（已填写的文档仍只能用 edits 修改）；
- 未被更新的草稿不能交付（提交时提示“仍是平台草稿”）。
- 渐进发布只保存进度，不放行等待该文档的任务：下游在负责人提交任务后开始，或在负责人发布时带 `ready=true`（文档已完整、任务尚未结束，例如契约先于实现）后开始。规则见 [task-planning.md](task-planning.md#依赖到交付物needs)。
- `ready` 的提示：task_brief 对本任务要发布的每份文档都提示“全部章节写完后以 `ready=true` 发布，之后最多一轮通读修正”。某次发布第一次填满所有草稿占位（上一版还有占位、还是平台草稿，或者没有上一版），且文档尚未 ready 时，发布回执带一次 `ready_hint`。不带编辑的 change 只用来标记 ready。`ready`、`based_on` 也可以写在顶层，作为每个 change 的默认值（不写进 schema，不增加每次调用的开销）。发布参数校验失败时，错误里附带一个最小可用的调用示例（`example_call`）。Blog2 的美工在 v6 写完全部章节后，又发了 12 个小修版本，始终没有标记 ready，前端因此晚了约 10 分钟开工。
- 每次发布的回执记录新版本的大纲和文档长度（存库和界面可见）；给模型的回执只有新版本号和新增或改名的章节 ID（`new_sections`）。章节 ID 由标题路径算出，没改标题的章节 ID 不变，所以不必每次返回整份大纲（Blog5 每次约 2,300 字符）。

这样证据和内容随工作逐步落盘，即使执行中断，已完成的部分也保留在文档中；配合工作记录与续跑，不再出现“最后统一写报告、一次失败全部丢失”。

## 回归覆盖

`tests/test_documents_progressive.py` 覆盖整篇读取与分页、草稿的章节与语言、幂等、草稿不能交付、填写后在提交时放行下游、未填写的草稿可整体替换而已填写的不行，以及调度执行时创建草稿并告知负责人。
