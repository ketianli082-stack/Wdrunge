## 0. 结论摘要

改六件事，按这个顺序做（第 5、6 件是 2026-10-06 追加的，对应复盘的 P0-1 和 P2-1）：

1. **流程**：新开发一律先由产品写需求文档，文档按“一级标题 = 模块、二级标题 = 需求 / 验收标准”组织；产品交付后唤醒 Leader，Leader 按模块给前后端建任务，一个任务只做一个模块，初始化单独成任务。这条不只写进提示词，还由平台在 `create_goal` / `create_task` 上检查。原因：同一份提示词，Blog4 用了产品，Blog5 没用，只靠提示词不稳定。
2. **提示词**：六个角色的提示词按你的定义重写，写成编号步骤和固定流程，去掉需要模型自己判断的条件句。示例（few-shot）放在三处：平台生成的文档草稿、任务说明、出错时的返回，尽量不放在每次调用都要重发的系统提示词里。
3. **工具调用容错**：LangGraph 没有模糊解析。LangChain 只在流式路径上补全缺失的括号。本平台还把每个工具都设成了严格模式，比 LangChain 默认更严。方案是关掉类型的严格模式（`"true"` → 布尔、数字字符串 → 整数由 Pydantic 默认转换完成）；不认识的参数改为忽略，并在返回里告诉模型；再加一层语法修复和“数组写成字符串”的修正，并处理目前没人处理的“无法解析的调用”。
4. **工具返回精简**：存库保留完整结果，给模型的只留它下一步用得到的字段。Blog5 里可去掉的约 16 万字符，占全部工具返回的 12% 左右。
5. **文档版本冲突（复盘 P0-1，3.7）**：任务依据哪份文档由任务声明决定，成员不再填版本号；平台记录每个任务读到了哪一版，提交时只比较读过的章节；冲突时返回改动的章节和发布摘要。Blog5 的三次冲突按新规则都不会发生。
6. **读文件与工作台（复盘 P2-1，第 7 节）**：通知里的 `force` 和工具参数对齐；同一文件的区间合并、空内容不上台；分段读取带上总长度；样式文件的索引列出全部类名。四条都是小改动，收益也小，见 7.1 的数据。

需要先说清的两点：

- **容错和精简的直接收益不大。** Blog5 的参数错误共 14 次，这一项能直接消掉其中 6 次；返回精简省的是结果体积的 12%，而结果的 64% 是文件和文档正文，不能删。这两项值得做（每次失败的调用都要多花一整轮），但省 token 的主要来源是第 1 项：Blog5 最大的两笔浪费（后端被驳回后多做 6.7M、第一个任务就做了骨架加三块功能）都出在流程上。
- **“写得更详细”有上限。** 六个角色的固定开销都已经贴着现有预算（Leader 13,494 / 13,500 估算 token）。系统提示词和工具说明每次调用都重发，Blog5 是 744 次。所以本方案的做法是把细节从“每次都发”挪到“用到才发”，并删掉提示词和工具说明之间的重复，而不是单纯加长。

## 2. 设计原则

1. **细节放在三层里最便宜的那一层。**
   - 每次调用都发：系统提示词、工具说明。只放角色定义、固定流程、参数的一句话说明。
   - 每个任务发一次：任务说明、平台生成的文档草稿。放本任务的范围、要读的章节、文档的结构示例。
   - 出错才发：失败返回。放这个工具的正确调用示例（现有的 `EXAMPLE_CALLS` 机制）。
2. **“什么时候调用”写在提示词里，“怎么调用”写在工具里。** 删掉两处重复的内容，腾出的预算给参数说明。
3. **给弱模型写的规则是固定流程，不是判断题。** “范围不清楚时交给产品”改成“新开发先建产品任务”，例外逐条列出。步骤编号，一步一件事。
4. **模型做不稳的事交给平台做。** 参数类型差一点的由平台规范化；流程顺序由平台检查；依赖版本由平台记录，不让模型自己报。
5. **示例只给结构，不给内容。** 用占位符（`<模块名>`），不用具体业务。弱模型会照抄示例里的内容。
6. **不改变“失败不隐藏”的原则。** 规范化只做不改变意图的类型修正；被截断的输出不修复；不认识的参数不默默丢掉。

## 3. 流程与平台检查

### 3.1 新开发的固定流程

```
用户请求
  └─ Leader：create_goal（写明需求文档路径）→ 只建产品任务 → 结束本轮
       └─ 产品：写需求文档（按模块）→ 发布就绪 → 任务进入待验收，Leader 被唤醒
            └─ Leader：对照用户原话验收需求 → 一次建完其余任务
                 ├─ 美工：主题说明 + 素材
                 ├─ 后端初始化（含 README、通用接口约定）
                 ├─ 前端初始化（等主题说明）
                 ├─ 模块 1：后端任务 → 前端任务（等模块 1 的契约文档）
                 ├─ 模块 2：…（同一角色的任务按模块顺序串行）
                 └─ 测试：在线验证全部模块（依赖所有模块任务）
```

Bug 修复、视觉调整、接口变更、咨询维持现在的短流程，不经过产品。

### 3.2 需求文档的格式

路径 `docs/product/requirements.md`。结构：

```markdown
（第一个标题之前：概述——目标、假设、不包含，三五行）

# <模块名>

## 需求1：<一句话标题>
谁、在哪个页面、能做什么；页面上的区域和操作；数据和规则；为空或出错时显示什么。

## 需求2：<一句话标题>
…

## 验收标准
- <能在浏览器里操作并看到的一条结果>
- …

# <下一个模块名>
…
```

每个一级标题是一个模块；模块按开发顺序排列。

**平台改动（`app/collaboration/planning.py`）**

- 根因：现在的需求草稿模板是“背景与目标 / 范围 / 验收标准 / 待确认问题”四个二级标题，和按模块开发对不上，开发只能通读。
- 修法：
  1. 需求类文档的草稿模板改成上面的结构（两个带占位符的模块）。草稿本身就是给产品的示例，只在产品任务里出现一次。
  2. 需求类文档以 `ready=true` 发布时检查结构：至少一个一级标题；每个一级标题下至少一个“需求”二级标题，并且有一个非空的“验收标准”二级标题；没有残留占位符。不通过时返回缺的是哪个模块的哪一节。
  3. 每个模块的需求条数和验收标准条数设上限（建议各 5 条，见第 11 节），超过时提示拆成两个模块。
- 验证：`tests/test_documents_progressive.py`、`tests/test_document_release.py` 增加用例：合格文档通过；缺验收标准、残留占位符、没有一级标题各自被拒并指出位置。

### 3.3 一次读完一个模块

- 根因：`collaboration_read(section_id=…)` 只返回该标题的直接正文，不含子标题。按新格式，读一个模块要先读目录再逐条读需求，Blog5 里 78 次章节读取就是这样来的。
- 修法：`collaboration_read` 增加 `subtree=true`，返回该章节连同全部子章节的正文。任务说明里直接给出本模块的文档 ID、章节 ID 和版本，成员第一步照着调用一次。
- 验证：`tests/test_document_tools.py` 增加用例；工作台（`context_desk.py`）把带子章节的读取记成一个条目，后续对其中任一子章节的读取命中“已在工作台”。

### 3.4 需求先行的检查

- 根因：产品这一步现在只是提示词里的一句条件句，平台不检查。Blog5 里 Leader 没建产品任务，也没有任何东西拦它。
- 修法（`create_goal`、`create_task` 的规划检查）：
  1. `create_goal` 增加必填参数 `requirements`，两种取值：
     - `{"document": "docs/product/requirements.md"}`：需求文档的路径。可以是用户已经提供的文档，也可以是接下来产品任务要交付的文档。
     - `{"none": "<原因>"}`：这个目标不需要需求文档（例如修一个已定位的 Bug）。原因会记录下来并显示在目标上。
     这样“不写需求”就从无声的遗漏变成一条有记录、你看得见的决定。
  2. 目标登记了需求文档时，给产品以外的角色建任务前，该文档必须已发布就绪。否则拒绝，返回里写明下一步：“先给产品建任务并结束本轮，交付后你会被唤醒”。
  3. `create_goal` 的返回里给出项目现状（`backend`、`frontend` 是否已初始化，按是否存在 `backend/pyproject.toml`、`frontend/package.json` 判断），Leader 不用自己翻目录就知道要不要建初始化任务。
- 验证：`tests/test_task_planning.py` 增加用例：需求未就绪时建后端任务被拒；就绪后通过；`none` 带原因时通过并被记录。

### 3.5 产品交付后唤醒 Leader

- 现状：任务进入待验收（review）时调度器会唤醒 Leader。文档以 `ready=true` 发布只会放行等待它的任务；而模块任务此时还没建，所以只发布不提交的话没有人被唤醒。
- 修法：任务声明的交付物只有文档时，最后一份文档以 `ready=true` 发布成功后，平台直接把任务转入待验收并唤醒 Leader，产品这一轮到此结束，不需要再调用 `submit_task`。发布的返回里写明“任务已交付”。
- 实施时先确认：现有代码里 `became_complete` 和“已发布的共享文档算作已交付”是否已经覆盖了一部分。这一点我只读了相关函数，没有跑过。
- 验证：`tests/test_document_release.py`、`tests/test_coordinator.py` 增加用例：纯文档任务发布就绪 → 任务状态为 review → Leader 收到一次唤醒。

### 3.6 一个任务只做一个模块

- 根因：模块划分只写在提示词里。Blog5 的 Leader 把骨架和三块功能放进了同一个任务。
- 修法（`create_task`）：
  1. 增加参数 `module`：需求文档里的一级标题。给后端或前端建任务时，目标有需求文档就必须二选一：`module=<模块名>`，或 `module="init"`（初始化任务）。模块名在文档里不存在时拒绝，并列出文档里有的模块名。
  2. 同一角色、同一模块只能有一个未取消的任务；项目未初始化而该角色还没有 `init` 任务时，拒绝建模块任务并说明原因。
  3. 平台把模块的文档 ID、章节 ID、版本写进任务，并在任务说明里给出读取调用（见 3.3）。
  4. 契约文档一个模块一份：前端模块任务等待的契约文档，必须是同一模块的后端任务声明交付的那份。等待别的模块的文档时拒绝。通用约定（基础地址、鉴权、分页、错误格式）由后端初始化任务交付一份单独的文档。
- 这条规则约束的是任务的形状，不保证模块本身大小合适；模块大小由 3.2 的条数上限约束。
- 验证：`tests/test_task_planning.py` 增加用例覆盖以上四条。

### 3.7 依赖的文档版本由平台记录（复盘 P0-1）

**Blog5 的三次冲突**（数据库里的 `submit_task` 调用和任务记录）：

| 时间 | 提交者 | 成员在 `based_on` 里填的 | 当时的版本 | 这份文档和任务的关系 |
|---|---|---|---|---|
| 08:22:07 | 后端 | 设计 v1 | v5 | 任务没有声明依赖它（`needs` 为空），成员只读过空草稿的大纲 |
| 09:31:28 | 美工 | 设计 v5 | v6 | 自己的交付文档，v6 是自己 2 分钟前发布的 |
| 09:48:56 | 后端 | 设计 v5 | v7 | 同第一次，任务没有声明依赖它 |

三次的版本号都是成员在 `submit_task` 里自己填的，三次都不是任务声明的依赖。第一次之后后端读了整份设计，多做了 6.7M。

**根因**（四处代码）：

1. 依据由成员填写。`submit_task` 和 `create_task` 都有 `based_on` 参数，成员把看过一眼的文档也填进去。平台不记录任务实际读了哪份文档的哪一版（`service.read` 不知道是哪个任务在读）。
2. 比较的是整份文档的版本号。`service.py:147` 的 `_dependencies` 只要版本号不同就拒绝，不看改的是哪一节。
3. 报错只有一句 `Dependency changed: <文档 ID> is v<N>`，没有路径、标题和改动的章节。发布时平台算过改动的章节（`service.py:277–279`），只发给了订阅者。
4. 所有冲突共用一句建议（`validation.py:224`）：“重新阅读当前文档 / 任务 / 目标，把你的改动与它对齐”。成员照做，就读了整篇。

**修法**：依据由平台按事实记录，按章节比较，冲突时只说改了什么。

**（一）哪些文档算依据，由任务声明决定。** 一个任务的依据只有两类：

- 任务 `needs` 里的文档；
- 需求文档里本任务 `module` 对应的那个模块（3.6）。

成员只是读过的文档不算。`submit_task` 和 `create_task` 的 `based_on` 参数从给模型的结构里去掉；模型仍然传的话，按 5.2（二）忽略并提示。

**（二）自己的交付文档不算依据。** 任务 `documents` 里的文档由这个任务自己发布，提交时直接按最新版本记录。

**（三）平台记录每个任务读到了哪一版。** 在工具层（`tools.py` 的 `read`，那里知道是哪个任务）每次成功读到正文时，在任务记录上写下 `文档 → 章节 → 版本`。整篇读取和带子章节的读取（3.3）记下返回的全部章节；只读大纲不算读过。记录跟着任务走，重试和换上下文之后还在。

**（四）提交时按章节比较。** 对每份依据文档，只看这个任务读过的章节：该章节在读到的版本和当前版本之间正文是否不同（和发布时算改动章节用同一个比较）。

| 情况 | 结果 |
|---|---|
| 读过的章节都没变 | 接受提交，引用更新到当前版本，回执里写一句“<文档> 已到 v7，改动不在你读过的章节里” |
| 读过的章节有变化 | 拒绝，返回见（五） |
| 读过的章节被删除或改名 | 拒绝，列出原标题，让成员读一次大纲 |

没读过的章节变了不拦。成员的工作不可能建立在它没读过的内容上；那里新增的要求属于新的工作，应该由 Leader 改任务，不通过驳回提交来传达。

**（五）冲突时返回的内容。** 结构固定，示例里是占位符：

```json
{"error": "你读过的 2 个章节在读之后改了，提交没有执行。",
 "document": {"path": "<文档路径>", "title": "<标题>", "read_version": 5, "current_version": 7},
 "changed_sections": [
   {"id": "<章节 ID>", "title": "<章节标题>", "changed_in": [6], "summary": "<v6 的发布摘要>"}],
 "next_action": "只读上面这几节（collaboration_read 带 section_id）。和你的交付无关就直接再提交一次；有关就只改受影响的部分。超出本任务验收标准的内容不要自己做，用 collaboration_send 报给 Leader。"}
```

成员读完这几节，（三）的记录就更新到当前版本，再提交即可通过，不需要填任何版本号。

**（六）运行中的提醒用同一个判断。** 现在文档一发布，凡是 `based_on` 里有它的任务都会收到 `request_basis_changed`，不带章节。改成只有“读过的章节变了”的任务才收到，并带上（五）里的章节列表；这样成员在工作中就能看到，不用等到提交。

**（七）实现上的收口。**

- `_dependencies` 改成返回结构化的差异，由新的异常类型 `BasisChanged`（继承 `StorageConflictError`）携带；`validation.py` 对它用（五）的 `next_action`，其他冲突的通用建议不变。
- `mark_conflict` 现在靠字符串 `'Dependency changed:'` 判断原因（`service.py:1150`），改成按异常类型判断。
- `_dependencies` 的其他调用处（发布时一份文档引用另一份、决定引用文档、合并交付物）继续按整份文档比较，但报错同样带路径、标题和改动的章节。

**和复盘 P0-1 五条的对应**：① → （五）；② → （二）；③ 和 ④ → （四）；⑤ → （五）的 `next_action`，同时写进 `modules/worker.md`（4.3）。比复盘多出来的是（一）和（三）：复盘只改了冲突之后怎么办，这里先把“什么算依据”收窄。

**Blog5 的三次冲突按新规则重看**：第 1、3 次设计文档不是后端任务的依据，不比较；第 2 次是美工自己的文档。三次都不会发生。（四）的章节比较在 Blog5 里没有现成的实例：前端任务声明了依赖设计文档，设计从 v5 到 v7 改了三节，但前端没有走到提交。验证时用这段修订记录构造用例。

**验证**：

- `tests/test_collaboration.py`、`tests/test_delivery.py` 增加用例：未声明的文档变了不拒绝；自己的文档不冲突；读过的章节变了时返回章节列表，读完后再提交通过；没读过的章节变了时接受并在回执里注明；章节被删除时提示读大纲；`request_basis_changed` 只发给读过改动章节的任务。
- 用 Blog5 的三次 `submit_task` 参数和当时的修订记录重放，三次都应通过。

## 4. 提示词

### 4.1 写法

- 每个角色的提示词分成固定的几段：你是谁 → 技术栈或交付物 → 初始化任务做什么 → 模块任务的步骤 → 不做什么 → 交付什么。
- 步骤编号，一步一件事，用“做 / 不做”的直接说法。
- 调用参数的写法从提示词里移走，放到工具的参数说明里（4.4）。
- 总长度不超过现有预算。美工和测试的提示词变短，Leader 基本持平。改完用 `role_overhead()` 实测，数字写进实施记录。

下面是六个角色文件的草稿。措辞可以直接改。

### 4.2 角色提示词草稿

**`leader.md`**

```text
你是团队 Leader：识别用户意图，把工作派给对应成员，验收，向用户汇报。用户是负责人。
你不写代码、需求文档或设计，也不规定成员的实现方式和步骤。

一、先判断请求类型
- 新项目或新功能：走“二、开发流程”。
- Bug 修复、视觉调整、接口变更：直接派给责任人（前端、后端或美工），再由测试复验。归属不明先让测试定位；需求本身有歧义才找产品。
- 咨询或闲聊：直接回答，不建任务。

二、开发流程（按顺序，不跳步）
1. create_goal，requirements 填需求文档路径 docs/product/requirements.md。用户已经给了完整的需求文档时填它的路径，直接到第 3 步。
2. 只给产品建一个任务：把用户的原话交给产品，交付需求文档。然后用一句话结束本轮。此时不给其他人建任务。
3. 被唤醒后读需求文档的目录，对照用户原话验收：模块和需求不能超出用户的要求，超出的让产品删掉。通过后 complete_task。
4. 一次建完其余任务：
   - 美工：主题说明和素材。
   - 后端初始化、前端初始化（module="init"，项目未初始化时才建；前端初始化等待主题说明文档）。
   - 需求文档里的每个模块：一个后端任务和一个前端任务，module 填模块名；后端任务交付本模块的契约文档，前端任务等待这份文档。同一角色的任务按模块顺序依赖上一个。
   - 最后一个测试任务：在线验证全部模块，依赖所有模块任务。
5. 模块、需求和验收标准都来自需求文档。不自己增加模块，不在验收标准里添加文档没有的要求。

三、写任务
- 一个任务只做一个模块，或只做初始化。
- 任务正文写要达成的结果和要读的模块名，不写实现方式，不写平台机制、端口或工作区路径。
- summary 是群里显示的一句话，不超过 80 字。
- 运行的服务只在首次交付它的任务（初始化任务）上声明；README 只交给后端初始化任务。
- 失败、阻塞或等待验收的任务，在原任务上重试或返工，不新建同样的任务。

四、验收
- review 表示已交付待验收。以任务状态为准：成员在群里说“已交付”但任务不是 review 时，先 inspect_request 看原因。
- 按验收标准、交付路径和证据验收。通过则 complete_task；有具体缺陷则在原任务上 queued 返工，写清缺陷。
- 不无依据验收，不向用户谎报完成。

五、协调
- 派活立即返回，不表示成员已完成。处理完当前能做的决定后，用一句阶段摘要结束本轮；成员 @你、任务阻塞或交付时你会被唤醒。不轮询，不为了等待调用工具。
- 群里只发简短的派活、阻塞和结果；细节放任务正文和文档。
- 成员之间的专业问题由他们直接解决，你只处理范围、优先级和跨角色冲突。
- 最终回复说明整体完成情况、关键交付和需要用户决定的事，不贴技术文档，不提平台机制。
- 阶段结束或上下文变长时单独调用 checkpoint_context。
```

### 4.4 工具说明

- 根因：调用方法分散在提示词和工具说明两处，参数本身几乎没有说明。弱模型主要看参数结构来填值。
- 修法：
  1. 出过参数错误的工具，每个不直观的参数加一句说明，带一个取值示例。例如 `needs`：“本任务开始前必须就绪的交付物，例：[{"document": "docs/backend/api-<模块>.md"}]”；`ready`：“布尔值 true 或 false，不加引号”。先做 `create_task`、`collaboration_publish`、`submit_task`、`collaboration_read`、`collaboration_register_service`、`execute_command`。

  3. 对应的调用写法从 `modules/*.md` 里删掉（4.3）。
- 验证：`tests/test_overhead_budget.py` 保持通过（或按你定的新预算）；`tests/test_tool_validation.py` 里现有的结构断言保持通过。

## 5. 工具调用容错

### 5.1 现状：LangGraph 有没有模糊解析

没有。逐层看：

| 层 | 行为 |
|---|---|
| 模型返回（流式） | LangChain 用 `parse_partial_json` 拼装参数。它只做两件事：补上缺失的结尾括号和引号；把字符串里的裸换行转义。其他语法问题（多余的逗号、单引号、代码块包裹、`True`/`None`）不处理 |
| 模型返回（非流式） | `json.loads`，失败的调用进入 `invalid_tool_calls` |
| LangGraph `ToolNode` | 不解析、不修复。拿到已是字典的参数，用工具的 Pydantic 结构校验，失败交给 `handle_tool_errors` |
| 本平台 | `validation.py` 的 `tool()` 把每个工具的结构设成 `strict=True, extra='forbid'`。Pydantic 默认会把 `"true"` 转成布尔、`"3"` 转成整数；严格模式下不转。所以本平台比 LangChain 默认更严。Blog5 里 `ready: "true"` 被拒 5 次就是这个原因 |

现有的宽容是逐个工具手写的（`Publish.change_defaults` 接受顶层的 `ready`、`based_on` 和数字字符串形式的 `base_version`），没有通用机制。

读代码时还发现两个缺口，Blog5 的记录里看不出是否发生过（平台没有记录 `finish_reason` 和无法解析的调用）：

- `worker.py` 没有处理 `invalid_tool_calls` 的分支。模型发出一个解析不了的调用时，这一轮既没有工具结果，也没有告诉模型错在哪。具体后果我没有复现。
- 流式路径会把被截断的参数补全成合法 JSON。如果模型的输出因为长度上限被切断，一个只写了一半的文件内容可能被当成完整调用执行。主调用上没有对 `finish_reason == 'length'` 的检查。

### 5.2 设计：放宽校验，加一层规范化

分三部分。前两部分改的是校验配置，第三部分是新模块 `app/agents/tools/arguments.py`，在所有工具调用的同一个入口执行（成员的 `guarded_tools`，Leader 的 `team.py` 执行路径）。

**（一）关掉类型的严格模式。** `validation.py` 的 `tool()` 和 `payloads.py` 的三个基类去掉 `strict=True`，交给 Pydantic 的默认转换。不用自己写代码。我用一个小模型实测过两种配置：

| 传入 | 现在（严格） | 关掉之后 |
|---|---|---|
| `ready: "true"` | 拒绝 | 接受 |
| `base_version: "3"` | 拒绝 | 接受 |
| `documents: "[\"a.md\"]"`（数组写成了字符串） | 拒绝 | 拒绝，由（三）处理 |
| `documents: "a.md"`（数组只给了一个值） | 拒绝 | 拒绝 |
| `summary: 5`（文字给了数字） | 拒绝 | 拒绝 |

严格模式是 2026-10-03 的提交 `399d191` 加的，我没有找到记录下来的原因。

**（二）不认识的参数：忽略，并在返回里告诉模型。** 现在是整个调用被拒。改成：

- 去掉不认识的参数，其余参数照常校验和执行。任何层级都一样（顶层、`changes[0]`、`edits[4]`）。
- 返回的最前面加一条提示，例如 `"notice": "force 不是 read_project_file 的参数，已忽略。"`。调用因为别的原因失败时，这条提示同样带在失败返回里。
- 被忽略的参数名记入工具调用记录，用来统计哪些工具的说明容易让模型写错。

Blog5 里不认识的参数一共 2 次，按这个规则重看：

| 调用 | 现在 | 改后 |
|---|---|---|
| `read_project_file` 多传 `force: true`（来自平台自己写错的提示，复盘 A5） | 被拒，重试一轮 | 正常读取，带一条提示，省一轮 |
| `collaboration_publish` 的一条 `insert_section` 编辑把 `new_text` 写成了 `content` | 被拒：“content 不允许” | 仍然失败（`insert_section` 必须有 `new_text`），但返回同时说明“content 不是参数”和“缺 new_text”，比现在清楚 |

**一种情况例外，需要你定（第 11 节第 10 项）：** 不认识的参数名和一个没有传的可选参数很像（例如 `dependancies` 对 `dependencies`）。这时忽略会改变调用的含义：`create_task` 会建出一个没有依赖的任务，提示到达时任务已经建好。我的建议是这种情况仍然拒绝，并在错误里写“你是不是想写 dependencies”。Blog5 里没有出现过这种情况，这条是按代码推出来的。

**（三）规范化模块 `arguments.py`。**

第一步：语法修复（原始字符串 → 字典），只对解析失败的调用做，按顺序尝试：

1. 去掉包裹的代码块标记和 JSON 前后的说明文字。
2. 结尾多余的逗号；单引号；`True` / `False` / `None`；没加引号的键名。
3. 字符串里未转义的换行和制表符。
4. 字符串已经闭合、只缺结尾的 `}` 或 `]`。

不修复，直接拒绝并说明原因：

- 响应的 `finish_reason` 是 `length`，或者需要闭合一个没写完的字符串才能解析——这是输出被截断。返回“调用被截断，没有执行；把内容分成几次写”。
- 修复后不是一个对象。

仍然无法解析的调用，返回一条正常的工具错误（带这个工具的示例调用），不再没有回应。

第二步：Pydantic 默认转换覆盖不到的结构修正。规则由工具的 JSON 结构驱动，对所有工具一视同仁：

| 规则 | 例子 | 依据 | 建议 |
|---|---|---|---|
| 结构要数组或对象，收到能解析成该类型的字符串 | `artifacts: "[\"a.py\"]"` → `["a.py"]` | `validation.py` 的注释记载为 Qwen 的已知行为；Blog5 未出现 | 做 |
| 结构要数组，收到单个合法元素 | `dependencies: "id"` → `["id"]` | 无 | 先不做 |
| 键名只有大小写、下划线、连字符的差别，并且只对应一个参数 | `sectionId` → `section_id` | 无 | 先不做 |
| 整个参数被多包了一层 | `{"arguments": {…}}` → 内层 | Blog5 未出现；`modules/shared.md` 里有一句专门禁止它 | 先不做 |

“先不做”的三条在 Blog5 里一次都没有出现。（二）上线后，写错的键名会以“被忽略的参数”出现在记录里，有了数据再决定加哪条（第 11 节第 11 项）。

**仍然不做的：**

- 缺少必填参数不猜（缺 `goal_id`、缺 `section_id` 共 4 次），靠参数说明和失败返回里的示例解决。
- 有歧义的结构不猜（多个 change 共用一个顶层 `base_version`，2 次）。
- 不改变值的含义（不截断、不改大小写、不做近义词替换）。

类型转换和结构修正记入工具调用记录，不写进给模型的返回；只有（二）的“参数被忽略”会告诉模型，因为那是模型写的内容没有生效。

现有逐工具的类型特例（`change_defaults` 里的数字字符串处理）由 Pydantic 默认转换替代；它里面“把顶层字段分发到各 change”的结构处理保留。

### 5.3 文件编辑的匹配（可选，优先级低）

`write_project_file` 的 `old_text` 匹配失败 5 次（195 次写入）。可以在精确匹配失败时，按“忽略行尾空白和缩进差异”再匹配一次，仍要求唯一。这属于另一种意义上的“模糊”，会改动文件内容，风险比参数规范化高，建议先不做，看规范化上线后的失败分布再定。

### 5.4 预期效果和验证

- Blog5 的 14 次参数错误（复盘的口径）里，直接消掉 6 次：`ready` 类型的 5 次（关掉严格模式），多传 `force` 的 1 次（忽略并提示）。另外 4 次缺必填参数的，靠 4.4 的参数说明降低；`content` 写错的 1 次和顶层 `base_version` 有歧义的 2 次仍会失败，靠失败返回里的说明和示例纠正；`artifacts` 超 30 项的 1 次属于交付检查（复盘 P0-5）。
- 一次失败的调用要多花一整轮。14 轮在 744 轮里不到 2%。这一项的价值主要是稳定，不是省 token。
- 验证：
  - 新增 `tests/test_tool_arguments.py`：5.2 里每条“做”的规则一个用例；每条“不做的”一个用例（确认仍被拒绝）；截断的调用被拒且没有执行；不认识的参数在顶层和嵌套层都被忽略，并且返回里有提示。
  - `tests/test_tool_validation.py` 里“拒绝未知参数”的现有测试改成“忽略并提示”；如果第 10 项按建议做，再加一个“名字相近仍被拒绝”的用例。
  - 把 Blog5 的 790 次调用参数重放一遍：原来成功的调用，处理后参数必须逐字不变；上面 6 次应通过校验。

## 6. 工具返回精简

### 6.1 原则

- 存库和界面保留完整结果，只精简给模型的那一份。在工具结果写成消息的同一个出口处理（成员的 `guarded_tools`，Leader 的 `team.py`）。
- 四条通用规则：
  1. 不把调用参数原样返回（模型上一条消息刚写过）。
  2. 取默认值的状态字段不返回（`timed_out: false`、`truncated: false`、空数组）；只在为真或非空时出现。
  3. 没有任何工具接收的内部标识不返回（进程 ID、批次 ID、消息哈希、时间戳）。
  4. 路径一律用项目相对路径，不出现任务快照的绝对路径。
- 每个工具在定义处声明给模型的字段（和现有的 `context_policy` 声明放在一起）。没有声明的工具按原样返回，所以可以逐个工具迁移。

## 7. 读文件与工作台（复盘 P2-1）

复盘 A5 的四个缺陷。它们都不大，但各自让成员绕路，而且第 ① 条和 5.2（二）有冲突，要一起改。

### 7.1 Blog5 的数据

| 现象 | 数据 |
|---|---|
| “已在工作台上”的通知 | 全程 1 次；通知让成员传 `force=true`，`read_project_file` 不接受，成员改用两次 `search_code` |
| 同一文件多个区间 | 记录下来的 68 份工作台里，24 份有同一文件的多个区间，17 份的区间有重叠。重叠的文字平均占工作台的 0.6%，最多一次 5,900 / 43,798 字符（13%） |

### 7.2 ① 通知里的 `force` 和工具参数对齐

- 根因：通知的文字是写死的（`context_fold.py:489`，“Pass force=true to receive it anyway”），不看是哪个工具。工作台这一层对任何工具都认 `force`（`context_fold.py:744`），但只有 `collaboration_read` 声明了这个参数。
- 修法：
  1. `read_project_file` 增加 `force` 参数。工作台的键已经会去掉它（`context_desk.py` 的 `TRANSIENT_ARGS`），不需要别的改动。
  2. 通知的文字按工具的参数结构生成：声明了 `force` 的才提它。
  3. 加一条测试把规则固定下来：凡是结果可能被换成“已在工作台上”通知的工具，都必须声明 `force`。
- 和 5.2（二）的关系：不改的话，校验层会说“`force` 不是参数，已忽略”，工作台层却照它执行，两处说法相反。所以这一条和 5.2 放在同一阶段。
- 开销：多一个布尔参数。测试角色现在是 14,488 / 14,500，这一项计入第 8 节的开销核对。

### 7.3 ② 同一文件的区间合并，空内容不上台

- 根因（`context_desk.py`）：
  - 条目的键是 `[file, 路径, offset, 请求的 limit]`，同一文件每个不同的区间各占一条。
  - `covers` 只认整份文件的条目，所以读一个已在台上的区间内部，不会得到通知。
  - `admit` 不看内容，空串也上台。
- 修法：
  1. 正文为空的读取不上台。
  2. 文件条目记录实际的区间 `[起点, 起点 + 正文长度)`，不再用请求的 `limit`。`covers` 按区间包含判断，读台上某个区间的内部也返回通知。
  3. 上台时，和同一文件已有的区间重叠或相接的，合并成一条：正文拼接，阅读记录取并集。重叠部分文字不一致说明文件在两次读取之间变了，这时丢掉旧条目，只留新读到的。合并后从 0 开始并且读到了文件末尾的，就是整份文件的条目。
  4. 合并后的长度不超过 30,000 字符，这是 `read_project_file` 单次读取的现有上限，超过就不合并，保证刷新时仍是一次读取。
- 文档条目按章节存放，没有这个问题，不动。
- 预期：省的空间很小（平均 0.6%）。主要作用是条目变少、区间内的重复读取能得到通知。合并后的条目更大，被淘汰时是整条一起走，这一点在重放里观察。
- 验证：`tests/test_context_desk.py` 增加用例（重叠、相接、不一致、超过上限、空内容、合并成整份）；用 `backend/scripts/replay_context.py` 重放 Blog5 前端线程，对比条目数、通知次数和淘汰后又读回的次数。

### 7.4 ③ 分段读取带上总长度，越界时说明

- 根因（`read_project_file.py:29`）：`content[offset:offset+limit]`，偏移超过文件长度时得到空串。总字符数只在 `include_hash=true` 时才返回。成员不知道文件多长，只能猜偏移。
- 修法：
  1. 偏移超过文件长度时返回 `[offset 10100 处没有内容；文件共 9352 字符]`（按 7.3 不上台）。
  2. 分段读取（`offset > 0` 或者被截断）的结尾写明位置：`[characters 9800–13400 of 23528; next_offset=13400]`，没有后续时不带 `next_offset`。一次读完整份文件的返回不变，不增加字符（198 次里的 121 次）。
  3. 这个结尾标记现在由三处各自用正则解析（工具本身、`context_desk.parse_file`、`context_fold.py:834`）。改成一个共用的解析函数，三处都调用它。
- 可选，需要你定（第 11 节第 14 项）：**按行读取**。代码索引给成员的是行号（`L12 def …`），并写着“只读你需要的行”，但读文件的工具只接受字符偏移，成员要自己把行号换算成字符数。3 次越界和多个重叠区间都是猜偏移的结果。给 `read_project_file` 加 `start_line` 和 `line_count`，工具内部换算成字符区间，返回里同时写行号和字符位置；工作台的键按返回的字符区间计算。代价是多两个参数，以及工作台的键要从“按参数算”改成“按返回算”。我的建议是做，和上面第 2、3 点一起改，因为它们动的是同一个返回格式。
- 验证：读文件工具的测试增加越界、分段、整份三种情况（现有测试里没有专门的读文件测试文件，放进 `tests/test_file_edits.py` 或新建一个）；`tests/test_context_*.py` 保持通过。

### 7.5 ④ 样式文件的代码索引列出全部类名

- 根因（`context_fold.py` 的 `STRUCTURE` 和 `structure`）：样式文件的索引是“行号 + 整行选择器”，每个文件最多 1,500 字符。`layout.css` 有 140 个类名，只列得出 40 个，其余写成“+124 more”。成员想知道有没有某个类，只能 grep。
- 修法：样式文件的索引改成去重后的类名列表，按首次出现的顺序，不带行号和花括号。其他类型的文件不变。原则是索引列出“别的文件会按名字引用的东西”，对样式文件就是类名。
- 用 Blog5 的 7 个样式文件实测，每个文件的上限仍是 1,500 字符：

| | 现在 | 改后 |
|---|---|---|
| 能列出的类名 | 162 / 339 | 289 / 339 |
| 列不全的文件 | 4 个 | 1 个（`layout.css`，90 / 140） |

- 要全部列出，`layout.css` 需要 2,459 字符。是否为样式文件提高单文件上限由你定（第 11 节第 15 项）；我的建议是先不提高，因为改用 Element Plus 之后手写样式应该明显变少。
- 这一条只保证索引里有类名，不保证成员会去看索引而不是 grep。重跑时统计 grep 样式文件的命令数（Blog5 是 31 条）。
- 验证：`tests/test_context_layers.py` 增加样式文件的用例（去重、顺序、超出上限时的尾注）。
