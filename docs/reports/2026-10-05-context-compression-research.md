# 上下文压缩策略调研（2026-10-05）

起因：两个问题。① 原文层是 30K 估算 token，一次工具调用就可能超过它，怎么办？② 能不能按时间压缩，也就是只压缩几分钟以前的消息，recall 之后重新计时？

本文只做调研和数据分析，**没有改代码**。外部资料见文末，内部数据来自 Blog2 快照和全部历史运行的 `agent_usage` / `tool_calls`。

---

## 0. 结论

| 问题 | 结论 |
| --- | --- |
| 单次结果会超过 30K 吗？ | **会。** 读一份中文文档最多 30,000 字符，约 45K 估算 token；一轮里并行读 4 节可以到 70K 以上。当前实现在这种情况下有两个缺陷：这一轮在下一次调用时就直接变成指针；它还会挡住更早的轮次，让它们也全部变成指针。 |
| 别人怎么限制单次结果？ | 都按 token 或字节给**单条结果设上限**，超出部分存起来，并告诉模型怎么取：Codex `tool_output_token_limit`（文章引用的默认值为 16,000）；OpenCode 2,000 行 / 50KB，全文另存为文件；我（Claude Code）这次会话里也看到大输出被存成文件，只放 2KB 预览。**应该按 token 封顶**，你的判断和业界一致。 |
| 按时间压缩可行吗？ | **作为保留规则不可行，作为“什么时候压缩”的信号有用。** 没有找到任何工具按墙钟时间决定保留什么：都按条数（最近 N 次、最近 M 轮）或 token 量。我们的数据：5 分钟窗口里的内容中位数 34K～56K、峰值 112K，超过整个预算；而且单次调用耗时从几秒到 343 秒不等，同样 5 分钟对应的轮数差别很大。 |
| 你的直觉对在哪里？ | “最近用过的不该压缩”是对的：65% 的重读发生在上一次读取后 5 分钟内，41% 在 60 秒内。“recall 重新计时”等于按最近使用排序（LRU），现在的实现已经是这样：重读和 recall 都会生成一份新的原文，排在最新位置。 |
| 时间真正该用在哪？ | 缓存。实测 DashScope 隐式缓存在 10 分钟内基本都能命中；超过 10 分钟，约一半调用完全没有命中。缓存已经失效时压缩没有任何缓存损失，可以趁机压得彻底一些。但同一线程里间隔超过 10 分钟的调用只占约 1%，收益不大。 |
| 30K 合适吗？ | 合适，是收益曲线的拐点。重读时上一份副本仍在窗口内的比例：15K 47%，**30K 62%**，45K 70%，60K 75%。从 30K 加到 60K，每次调用要多带一倍的原文，只多覆盖 13 个百分点。 |
| 调研中的新发现 | **47% 的重读发生时，上一份副本很可能仍是原文、就在上下文里；53 次读取返回的内容与之前一模一样。** `collaboration_read` 本来有“已在上下文中”的去重，但 Blog2 里一次都没触发：每次折叠都会重置整个线程的读取回执，而 Blog2 折叠了 86 次。这是重读的另一个根因，和窗口大小无关。 |

## 1. 单次结果有多大

| 工具 | 单次上限 | 最大估算 token（字节/2） |
| --- | --- | --- |
| `read_project_file` | 30,000 字符 | 英文代码约 15K；中文约 45K |
| `recall_context` | 30,000 字符 | 同上 |
| `collaboration_read` | 12,000 字符 | 中文约 18K |
| 命令输出 | 4,000 字符（头 800 + 尾 2,400） | 约 2K～6K |

上限按字符算，没有考虑中文 1 个字约 1.5 个估算 token，这是根因。

当前分层代码（`tier_bounds`）遇到超大轮次时的行为：
1. 当前轮无论多大都保持原文，模型能看到一次。
2. 下一次调用时，这一轮放不进原文层（30K），也放不进摘录层（15K），**直接降为指针**。模型只在一次生成里看得到这份内容。
3. 分层是从新到旧连续累计的，碰到第一个放不下的轮次就停。所以**更早的所有轮次也都降为指针**，摘录层等于不存在。
4. 单轮超过整个预算（约 90K）时进入摘要流程，所有工具结果（包括最新一轮）都会被截到 3,000 字符。

## 2. 别人怎么做

| 系统 | 单条结果上限 | 旧结果怎么处理 | 何时压缩 | 摘要 | 来源可信度 |
| --- | --- | --- | --- | --- | --- |
| Anthropic API · context editing（`clear_tool_uses_20250919`） | — | 清除最旧的工具结果，换成占位；默认**保留最近 3 次工具调用**；`exclude_tools` 永不清除 | 默认输入超过 **100,000 token**；`clear_at_least`：一次能清掉的量不够就不清，因为“清除会让缓存失效，要清得值” | 另有服务端 compaction，可以保留最近几轮原文 | 官方文档 |
| Claude Code | 大输出存成文件，上下文里只放预览和路径；读文件有行数/token 上限，超出要求分页 | microcompact：清除旧的工具结果（读文件、grep、bash 输出等），调用记录保留 | auto-compact：接近上限时整段摘要；摘要后重新附上最近读过的文件 | 整段摘要 | 前两点是我在本次会话中观察到的；microcompact 细节来自第三方文章，官方没有公开阈值 |
| Codex CLI | `tool_output_token_limit`（文章引用的默认值为 16,000） | 压缩时丢弃全部助手回复和工具结果 | 上限按窗口的 90% 封顶 | 保留 1 条摘要 + 最近约 20K token 的用户消息；重新读取最近编辑的 5 个文件（共 50K） | 第三方文章（引用配置项） |
| OpenCode | 2,000 行或 50KB，全文另存为文件，7 天后清理 | `prune`：从新往旧走，**最近 2 个用户轮次不动，最近 40,000 token 的工具输出不动**，更早的输出标记为已压缩；可释放量不到 **20,000** 就不压缩；skill 类工具永不压缩 | 上下文溢出时 | 有 | 源码常量（`PRUNE_PROTECT`、`PRUNE_MINIMUM`）+ 文档 |
| OpenHands | — | ObservationMasking：最近 `attention_window` 个事件保留观察结果（默认 100） | 事件数超过 `max_size` | LLMSummarizing：保留开头 `keep_first` 个事件和最近的事件，中间摘要 | 官方文档 |
| JetBrains 研究（SWE-agent，SWE-bench Verified） | — | **观察屏蔽：保留最近 M=10 轮，更早的换成占位** | — | 摘要：每 21 轮摘要一次，保留最近 10 轮 | 论文 |
| Manus | — | 可恢复的压缩：网页内容可以丢，保留 URL；文档内容可以丢，保留路径 | 以 KV 缓存命中率为第一指标，上下文尽量只追加 | — | 官方博客 |

**JetBrains 论文的关键数据**：
- 简单屏蔽和 LLM 摘要相比，成本都降了约一半（Qwen3-Coder 480B：屏蔽 −52.7%，摘要 −50.4%），解决率相当或略高（屏蔽 54.8% vs 原始 53.8%）。
- 摘要反而让轨迹**变长约 15%**：模型看不到失败的细节，会多做几步。
- 混合策略（先屏蔽，摘要只作最后手段）比纯屏蔽再便宜 7%，比纯摘要便宜 11%。
- 摘要调用本身占单题成本最多 7.2%。

**共同模式**：
1. 单条结果有上限（token 或字节），超出部分存起来，给出找回方式。
2. 保留窗口按条数或 token 量计算，**没有一家按墙钟时间**。
3. 改写历史要“改得值”：Anthropic 的 `clear_at_least`、OpenCode 的 `PRUNE_MINIMUM` 都和我们的 12K 批量阈值是同一个思路。
4. 摘要是最后手段，日常靠屏蔽或指针。
5. 压缩要可恢复：保留路径、URL 或 ID。

我们的设计（30K 原文 + 15K 摘录 + 指针 + 12K 批量 + 摘要兜底）和 OpenCode（40K 保护 + 20K 最小量）、Anthropic（100K 触发 + 至少清掉多少）结构上一致。**缺的是第 1 条：单条结果按 token 封顶。**

**缓存有效期**：Anthropic 默认 5 分钟，每次命中刷新（可选 1 小时）。DashScope 显式缓存 5 分钟，命中后重置，命中部分按输入单价约 10% 计费，新建缓存按 125% 计费。隐式缓存的官方说法是“有效期不确定，定期清理长期未使用的”，命中部分约按 20% 计费，最少 1,024 token。

## 3. 我们自己的数据

### 3.1 缓存命中率与调用间隔（全部历史，1,135 次 work/coordination 调用，均为 qwen3.8-max）

| 距同一线程上一次调用的间隔 | 次数 | 命中率中位数 | 几乎未命中的次数 |
| --- | --- | --- | --- |
| < 10 秒 | 938 | 94% | 5 |
| 10–60 秒 | 147 | 95% | 2 |
| 1–3 分钟 | 7 | 94% | 0 |
| 3–5 分钟 | 3 | 91% | 0 |
| 5–10 分钟 | 9 | 86% | 0 |
| **> 10 分钟** | 13 | **0%** | **7** |

DashScope 隐式缓存在 10 分钟内基本都在；超过 10 分钟，约一半调用完全失效。注意：5 分钟以上的样本只有 25 个，结论只能算方向性的。另外，同一线程内间隔超过 1 分钟的调用只占约 3%（32/1,117）。

### 3.2 调用耗时

中位数 9 秒，p75 20 秒，p90 40 秒，最长 343 秒；超过 120 秒的有 16 次。所以 5 分钟可能是 30 轮，也可能是 1 轮。

### 3.3 重读的时间与 token 距离（Blog2，同一文件或同一文档章节，共 280 次重读）

| 上一次读取后多久重读 | 占比 |
| --- | --- |
| ≤ 60 秒 | 41% |
| ≤ 2 分钟 | 49% |
| ≤ 5 分钟 | 65% |
| ≤ 10 分钟 | 79% |

| 如果原文窗口是 | 重读时上一份仍在窗口内 |
| --- | --- |
| 15K | 47% |
| **30K** | **62%** |
| 45K | 70% |
| 60K | 75% |

注：同一文件按不同偏移翻页也算作“重读”，所以这两个比例偏高。

### 3.4 “最近 5 分钟”窗口能装多少（Blog2，工具结果的估算 token）

| 角色 | 中位数 | p90 | 最大 |
| --- | --- | --- | --- |
| 前端 | 55,789 | 81,057 | 87,160 |
| 后端 | 34,347 | 79,546 | **111,757** |
| 美工 | 21,413 | 34,177 | 37,295 |

按时间保留时，原文量随模型速度和读取频率在 2 万到 11 万之间波动，峰值超过整个上下文预算（约 9 万）。

### 3.5 重复读取与失效的去重

- Blog2 的 452 次读取中，**53 次与之前一次参数完全相同、返回内容也完全相同**，这些结果共约 8.2 万估算 token，而且每份之后还会随每次调用重复发送。
- 47% 的重读发生时，上一份副本在 15K 以内，很可能仍是原文、就在上下文里。也就是说，**相当一部分重读不是因为内容被折叠了，而是模型没意识到内容还在**。
- `collaboration_read` 本来有去重：同一修订已在上下文中时，返回 `already_in_context` 而不是全文。但 Blog2 里一次都没触发：`ContextMemory.record()` 在**任何一次**压缩（包括只折叠了很早的结果）时，都会重置整个线程的读取回执，而 Blog2 折叠了 86 次。`read_project_file` 则完全没有这类去重。

## 4. 对“按时间压缩”的评估

| 方面 | 评估 |
| --- | --- |
| 最近用过的不压缩 | ✔ 方向正确（3.3）。按 token 量计算的窗口加上“重读/recall 产生新副本”，已经实现了按最近使用排序。 |
| recall 后重新计时 | ✔ 已经等价实现：recall 的结果是一条新消息，排在最新位置；旧副本被标记为已被取代。 |
| 用墙钟时间决定保留 | ✘ 窗口内容量不可控，会超预算（3.4）；和模型速度、等待时间耦合（3.2）；没有先例（第 2 节）。 |
| 用时间决定什么时候压缩 | ✔ 有道理：缓存已经失效（间隔超过约 10 分钟，或上一次调用命中率很低）时，压缩没有缓存损失。但这类调用只占约 1%，属于小优化。 |

## 5. 建议（供讨论，未实现）

按预期收益排序：

1. **单条结果按 token 封顶（根因修复）**：在所有工具结果进入上下文的同一个位置统一处理，不在每个工具里各写一套。
   - 上限建议约 8K～10K 估算 token，在 30K 原文层里至少能同时放下 3 条。
   - 可分页的读取（文件、文档、recall）返回 `next_offset`；其他输出保留开头和结尾，全文进审计，用 `recall_context` 分段取回。
   - 与 Codex 的 `tool_output_token_limit`、OpenCode 的 50KB、Claude Code 的“存文件 + 预览”是同一做法。
2. **读取去重按“是否仍是原文”判断**：同一资源（相同路径和区间，sha 未变）的上一份副本如果仍在原文层，就返回“内容未变，见消息 X”，不再重发全文；副本已经降为摘录或指针时，才返回全文。`collaboration_read` 的回执也改为按消息判断，不在每次折叠时整体重置。直接针对 3.5 那 53 次完全相同的读取，以及“内容还在却重读”的情况。
3. **分层修正**：放不进原文层的轮次按单条结果拆开，最新的结果尽量保持原文，其余降为摘录，不直接降为指针；继续往前累计时跳过它，不在它这里停下；摘要流程不截断原文层。
4. **原文层保持 30K**：数据显示是拐点（3.3）。加到 45K 或 60K，每次调用都要多带原文，覆盖率只多 8 到 13 个百分点。
5. **缓存冷了时顺带压缩**（小优化）：间隔超过约 10 分钟，或上一次调用命中率低于 20% 时，不等攒够 12K 就压缩。阈值从 `agent_usage` 的实际命中数据持续校准。
6. **不做**：按墙钟时间决定保留什么。

验证方式：以上都可以先用 Blog2 的 `tool_calls` 原始结果重放，量化重读次数和单次上下文的变化，再跑 Blog3。
