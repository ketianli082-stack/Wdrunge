## 3. 问题根因

分四类：
- **A. 平台缺陷**：机制做错了，换模型也会出问题。
- **B. 规则与提示词**：机制没错，但给模型的约束或引导不够。

### A. 平台缺陷

#### A1. 有效工作窗口太小，折叠后的重读没有保留机制（P0）

**现象**：

| 指标 | 前端 | 后端 | 测试 |
| --- | --- | --- | --- |
| 只读轮占比（平台口径） | 62%（31.97M） | 49% | 47% |
| 同一尝试内对同一目标的重读 | **470 / 680 次读取（69%），995K / 1.47M 字符** | 53% | 50% |
| 纯重读轮（这一轮读的全是本次尝试读过的） | 282 轮，**13.58M** | 92 轮，3.94M | 42 轮，1.97M |
| 折叠次数 | 前台线程 47 次 / 4.6 小时，后台线程 47 次 / 3.1 小时 | | 24 次 |

读放大：

| 被读对象 | 大小 | 被读了多少 | 次数 |
| --- | --- | --- | --- |
| 设计文档 v9/v10 | 23.5K 字符 | **274K 字符（11.7 倍）** | 137 次 |
| 需求文档 v7 | 15.3K 字符 | 134K 字符（8.8 倍） | 65 次 |
| 契约 v14 | 17.0K 字符 | 105K 字符（6.2 倍） | 46 次 |
| `admin.css` | 26.6K 字符 | 84K 字符 | 17 次 |
| `schema.d.ts`（生成文件） | 1,590 行 | 68K 字符 | 25 次 |

**典型片段（后台前端第 1 次尝试）**：设计文档同一组章节（`da6b…`、`dee7…`、`529b…`、`666c…`）在 18:38、18:43、18:48、19:04、19:12 各读一遍；`client.ts`、`routes.ts`、`App.tsx` 每轮折叠后重读。上下文曲线是锯齿：涨到约 50K，折叠回 35K，再读回 50K。

**根因**（都是通用机制）：

1. **窗口偏小**。L2 只保留最近约 30K 估算 token 的工具结果原文，更早的折成 600 字符的摘录；预算是 `窗口 × 0.75`。按模块拆任务后，单个模块的工作集仍然包括：
   - 设计的 4 个页面章节、需求 B 章、契约第 6 章（约 15K 中文字符）；
   - 生成的 API 类型；
   - 十几个要复用的模块；
   - 一个上千行的样式文件。
   
   这放不进原文层，于是每 10 轮左右折叠一次，模型再读回来。

2. **估算系统性偏高 1.55 倍**。
   - `estimate()` 用 UTF-8 字节 / 2。中文一个字 3 字节，估成 1.5 token；qwen 的分词器大约 1 字 1 token 左右，代码也比字节 / 2 少。
   - 对后台线程 66 个 checkpoint 做回归：**实际输入 ≈ 0.643 × 估算 + 3.9K**（估算只算消息，实际含工具定义）。即 1 估算 token ≈ 0.64 实际 token。
   - 后果：
     - 原文层 30K 估算 ≈ **19K 实际**；
     - 预算 98K 估算 ≈ **63K 实际**；
     - 段摘要在 80% 预算（约 78K 估算，约 50K 实际）就提交。
   - 本次主模型最大输入 61.7K，正好卡在这个换算后的上限。128K 窗口实际只用了一半。
   - **阈值是你定的（原文层 24～30K），我没动；问题在单位**：定阈值时用的是估算单位，实际比想象的小三分之一。

3. **被读回来的东西不会比第一次留得更久**。平台没有区分“读一次就够”的内容和“工作集核心”。同一个章节被折叠、重读、再折叠，没有任何记录让它下次多留一会儿。这和缓存颠簸（thrashing）是同一个问题，标准做法是：被驱逐后又被访问的条目，提高保留优先级。

4. **读暂停被绕过**（Blog3 方案 P0-3 ③）：
   - 第 12 轮提醒后，模型最常见的反应是写一次小文件（13 次），读取计数清零；
   - 第 24 轮暂停提示后，写一条 `journal next`（4 次），读取立即恢复；
   - 所以拒绝读取从没发生。
   
   这说明“限读”打不到根上：模型读，是因为写这个文件真的需要那些内容，而那些内容刚被折掉。

#### A2. `browser_verify` 的断言语义容易误用，失败反馈不足（P0）

**数据**：前端 139 次、测试 99 次，共 238 次，**失败 154 次（65%）**。按 `turns` 归类，浏览器轮花了 **10.96M**（前端 6.55M + 测试 4.41M），每次失败后通常还跟着几轮读源码、curl 核对期望值。

| 失败类型 | 前端 | 测试 | 例子 |
| --- | --- | --- | --- |
| 选择器命中多个元素（Playwright 严格模式） | 33 | 13 | `.article-card` 命中 10 个；`.hljs-keyword` 命中 32 个 |
| 期望值和实际内容不符（期望是猜的） | 23 | 17 | `'找到 1 篇'` 实际 `'找到 3 篇'`；`'代码技术博客'` 实际 `'陆野的代码博客'` |
| 等待超时（选择器猜错或元素不出现） | 23 | 14 | `.list-head__subject` 不存在 |
| **只差空白或换行** | 10 | 2 | `'分类：前端'` 实际 `'分类：\n前端'`；面包屑 `'首页 / 数据库 / …'` 实际 `'首页\n/\n数据库\n/\n…'`；`'#并发'` 实际 `'#\n并发'` |
| 只差顺序 | 1 | 0 | 导航顺序 |
| 页面有控制台或 HTTP 错误 | 6 | 6 | |
| 选择器语法错误、参数错误、连接拒绝 | 4 | 2 | `:text-is(…) ~ ..`、`tr text=撤回` |

**根因**：
1. `browser_runner.py` 的 `assert_text` 取 `locator.inner_text()` 做子串比较。`inner_text` 在块级、flex 子元素之间插换行，人眼看到的“分类：前端”在比较时是“分类：\n前端”。不归一化空白，就会出现“内容对、断言错”。
2. `page.locator(selector)` 是严格模式，命中多个就抛错。模型写的是 CSS 习惯（`.article-card` 表示“有卡片”），工具语义却是“必须唯一”。
3. 失败结果只回报“期望 / 实际 500 字符”和整页 `inner_text` 前 12,000 字符，没有给出**选择器实际命中了什么**（数量、每个元素的文本和类名）。模型只好读源码、猜下一个选择器，平均要试好几次。
4. 成功结果也回 12K 字符的整页文本，进上下文的量很大（浏览器结果合计 430K 字符）。

#### A3. 项目服务可以被 worker 停掉并从任务快照同名重启；尝试结束时一起被杀；还有一次停止原因不明（P0）

**证据**（从 `manage_process`、`execute_command` 结果里追踪 api 进程号）：

| 时间 | 进程 | 目录 | 事件 |
| --- | --- | --- | --- |

| 18:35 | 26846a44 | 项目根 | 仍在运行 |
| 20:59 | — | — | 前端 `detect_environment`：api `runtime.state = stopped`。**18:35–20:59 之间没有任何 agent 发出 stop，平台事件里也没有记录** |
| 21:51 | 315e9484 | **前端快照** | 前端从自己快照启动 api |
| 22:23 | 6441e9cd | 项目根 | 前端交付后，平台把它移回项目根 ✅ |
| 23:13 前后 | 5e9d2651 | 项目根 | 缺陷修复合并后，平台从根目录重启 ✅ |
| 23:14:48 | 5e9d2651 | 项目根 | **测试 `manage_process stop`**（Leader 让它“重启 api 使修复生效”，其实平台刚重启过） |

**问题**：
1. **worker 能停掉项目根的登记服务**。`3d8f72f` 防的是“运行中被快照替换”；先 stop 再 start 绕过了它。
2. **停掉之后，可以用同一个登记名从快照启动**。此后“项目服务 api”实际跑的是测试快照里的代码，而且归属于一个会失败的尝试。
3. **尝试结束（失败或取消）时，快照进程被杀，项目服务就没了**。没有自动恢复根目录副本，也没有事件通知 Leader。用户停止时 api 是否还在，取决于最后一次谁启动的。
4. **18:35–20:59 的那次停止原因不明**，数据库里查不到 stop 调用、退出事件或失败报告（`report_failure` 只在“从根目录重启失败”时调用）。它的直接后果是：后台前端 21:00 发现 api 停着，就自写了 mock 接口，用 mock 验证了 45 分钟（7.95M 的一部分）。需要复现排查。

#### A4. 步数上限仍是硬失败，“续接”只是再跑 250 轮（P0，Blog3 P1-2 未实施）

- 5 次 `GraphRecursionError`，每次约 250 轮、10.8～12.8M，合计 **59.3M**。
- `service.transition` 的规则：失败后第一次重排 `resume=True` 续接原线程，再失败才全新。数据显示**续接没有任何收益**：
  - 前台续接：250 轮，34 次写入，结局同样是撞上限；
  - 后台续接：250 轮，前 30 分钟还在重读（20:14–20:44），写完后又进 mock 验证循环。
- 真正起作用的是 Leader 在第二次失败后写的**收尾清单**：哪些已完成（文件、typecheck、build）、还剩哪几步、最多验证几项、期望值从哪取。配上全新上下文，26 / 44 轮就交付了。
- 失败事件仍然是 LangChain 的英文异常原文。

**和 Blog3 的“干净交接”有什么不同**：Blog3 是在实现中途（第 24 轮只读时）清上下文，刚读进来的工作集被扔掉，所以更糟。这次的全新尝试发生在**代码已写完、能编译**的节点，需要的上下文很少。两者的区别是“在哪个节点重开”。

#### A5. Leader 的 `enable_tools(commands)` 说启用了，`execute_command` 却不能用（P1）

- 16:19 Leader 调 `enable_tools(groups=["commands"])`，返回 `{"enabled": ["commands"]}`，状态 success。
- 16:20、16:20:53 两次 `execute_command`（curl 核对 openapi 里是否有 admin 路径）都返回 `"Unknown tool call"`。`team.py:529` 的 Leader 调度器只处理 `delegate_task(s)`、`enable_tools`、`recall_context` 等少数工具，其余一律返回这句话，而且记录状态是 success。
- Leader 因此无法核实 api 的状态，认定“api 仍在跑合并前的代码”，派了 `blog-api-rollout` 任务：**46 轮、1.38M、29 分钟**。后端最后确认平台早在 16:17 就从根目录重启过了。
- 23:14 Leader 又让测试“重启 api 使修复生效”，也是同一个盲区，直接引出了 A3 的第 2、3 步。

### B. 规则与提示词

#### B1. 验证范围没有边界

- 前台验收标准要求“实现加载 / 空 / 失败状态”。前端为了“验证”这些状态，写了桩接口（让接口返回 500、空列表、延迟），又为了验证窄屏导航溢出写了第二个桩，还写了 CSS 检查脚本。临时服务注册、注销、端口冲突，来回 30 次 `collaboration_register_service`。
- 后台前端在 api 停掉后（A3），没有报告阻塞，而是写了一个完整的 mock 后台接口（9.7K 字符，凭据都是猜的 `admin / admin123`），在 mock 上验证了 11 + 15 项。这些验证在真实接口上又做了一遍。
- 提示词里有“交付前自测”和“每片做一次真实运行检查”，但没有说：
  - 验证证据按验收标准逐条给，**一条标准一次检查**；
  - 依赖服务存在时用真实服务，不可用时**先报告阻塞**，不要自建替身；
  - 状态类标准（加载、失败）用代码审查加一次真实检查即可，不必为每种状态造后端。
- 反证：Leader 的两份收尾清单正好写了这些，于是 14 分钟、29 分钟就交付了。

#### B2. 文档超预算，直接放大了 A1

- 设计 23.5K 字符（预算 15K，超 56%），需求 15.3K，契约 17.0K、14 个版本。
- 设计里有大量前端用不到的细节（窄屏三行高度 56 / 40 / 52、命中区分类规则等）。前端为了“对齐”这些细节反复读取，还引出了一次设计矛盾和一次 v10 修订。

#### B3. 示例数据仍然写成了真文章

`seed.py` 527 行，12 篇已发布 + 2 篇草稿，含完整技术正文。产品需求 §7 仍然规定了篇数和内容组合，Leader 验收时以“需求第 7 节要求”为由认可。这块花费不大，但说明 Blog3 P2-1 的提示词没改到需求文档的写法。

### C. 纯模型错误

| 角色 | 错误 | 影响 |
| --- | --- | --- |
| 前端 | 断言期望值靠猜，不先取真实数据 | A2 里 40 次“内容不符” |
| 前端 | `journal next` 写了“下一步写编辑页”，随后 30 分钟还在读 | 后台续接前 30 分钟 |

## 10. 改进建议（按收益排序）

原则同前：通用机制，不针对 Blog4 的具体角色、文件或文档。

| 优先级 | 根因 | 通用修法 | 验证方式 |
| --- | --- | --- | --- |
| **P0-1** | A1 估算偏差 | **用实际计费校准估算**：每次调用后，用接口返回的 `prompt_tokens` 和本次发送内容的估算值，按线程维护一个滑动比值（初值 1.0，夹在 0.4～1.2）；所有阈值（原文层、摘录层、预算、段摘要触发点）都换算成实际 token 再比较。**阈值数值由你定**；本项只修单位，按你原来的 24～30K 理解，原文层会从约 19K 实际放大到 24～30K 实际 | 用 Blog4 后台线程 66 个点重放：校准后估算误差 < 10%；统计折叠次数和重读占比的变化 |
| **P0-2** | A1 重读颠簸 | **“驱逐后又被读回”的内容提高保留级别**：同一尝试里，某个读取目标（文件路径加内容哈希，或文档章节加版本）的结果被折叠后又被读回来，就标记为“热”。热内容在原文层里优先保留，不参与下一次折叠，直到文件被改写或超出热区预算（例如原文层的 40%，按最近使用淘汰）。被改写的文件，旧的热结果作废。**不新增模型调用，不改工具** | 用 Blog4 前端两条线程离线重放：同目标重读次数、纯重读轮 token。真实运行目标：前端重读占比从 69% 降到 30% 以下 |

### 10.1 模拟：折叠保护 10 分钟（2026-10-06）

**问题**：工具结果读进来后 10 分钟内不折叠，能省多少？

**方法**：用 Blog4 的真实调用序列离线重放，没有改平台代码。
- 从 `context_compactions` 的 fold / summary / checkpoint 记录里，对比 source 和 replacement，得到每个工具结果**第一次被折叠的时间**（2,312 条）。
- 同一次尝试里，对同一目标的再次读取，按三种情况归类：
  - 上一份还没被折叠（模型自己重读，规则管不到）；
  - 上一份已被折叠，且距上次读取 ≤ 10 分钟（**规则能避免**）；
  - 已被折叠，且距上次读取 > 10 分钟（规则管不到）。
- 文件被改写后，旧的读取作废，不算可避免。
- 目标判定分两种口径：
  - 宽口径：文件只看路径；
  - 严口径：文件看路径加读取范围。
  - 文档两种口径都看文档、版本、章节。
- **省下的**：一轮里的读取全部可避免，整轮去掉，按这一轮的实际 token 计。
- **多花的**：每次调用时，“10 分钟内读过、本来已被折叠、现在要保留”的结果，按 1 估算 token ≈ 0.643 实际 token 折算，加到这次调用的输入上。

**结果（前端，宽口径）**：

| 规则 | 能避免的重读 | 去掉的轮 | 省下 | 多带的上下文 | 净值 | 平均 / 峰值输入 | 超过现预算（约 63K 实际）的调用 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 现状 | — | — | — | — | — | 47K / 62K | 0 |
| 保护 5 分钟 | 12 / 315 | 3 | 0.13M | 0.72M | −0.60M | 48K / 72K | 8 |
| **保护 10 分钟** | **80 / 315（25%）** | **32 / 1,072** | **1.49M** | **2.95M** | **−1.47M** | **50K / 74K** | **47** |
| 保护 15 分钟 | 145 | 59 | 2.74M | 5.84M | −3.10M | 53K / 83K | 122 |
| 保护 20 分钟 | 201 | 83 | 3.90M | 8.13M | −4.23M | 56K / 87K | 187 |
| 保护 30 分钟 | 264（84%） | 118 | 5.58M | 10.71M | −5.13M | 59K / 109K | 280 |
| 读回即保留（原 P0-2，保留区 15K） | 117 次读取 | 71 | 3.38M | 7.49M | −4.11M | 55K / 76K | 252 |

- 严口径下，10 分钟只能避免 59 次，净值 −2.39M。
- 后端、测试的重读本来就少：10 分钟时分别去掉 4 轮、1 轮，净值 −0.16M、−0.19M。

**为什么 10 分钟几乎没用**：
1. **现在的折叠本来就不快**：一个结果从读进来到被折叠，中位数 7.8 分钟（四分位 4.9～11.6 分钟）。“10 分钟”对一半的结果只多保留了两三分钟。
2. **重读离上次读取很远**：被折叠后又读回来的那 315 次，距上次读取中位数 **16 分钟、29 轮**；10 分钟内的只占 25%，要覆盖 84% 得 30 分钟。
3. 中间这 29 轮里，模型在读工作集里的**别的**内容。工作集确实比窗口大，靠延长保留来覆盖它，上下文就要放大到平均 59K、峰值 109K。现预算装不下：30 分钟时有 280 次调用会超。
4. **多带的上下文每次调用都要付，省下的只是零散的几轮**，所以按总 token 算是净增。按缓存计价看：多带的部分大多命中缓存（0.2 倍价），省下的轮次按实际折算约 0.27 倍价。即便这样，10 分钟也只是大致持平。

**模拟管不到的部分**：
- 一阶核算假设模型其余行为不变。保留更多上下文后，模型有可能更早开始写（后台的主要文件实际上是在 15 分钟里写完的）。这只能靠真实运行验证，离线算不出来。
- 少折叠意味着少改写历史，缓存未命中会减少一些，这里没计入。

**结论**：
- 10 分钟保护**不建议实施**：最多避免 25% 的重读，净增约 1.5M，还有 47 次调用超出现预算。
- 按时间或按“读回即保留”去延长保留，在一阶核算下都是净增。重读是真实存在的（纯重读轮 13.6M），但它的根源是工作集比窗口大，不是窗口里的东西被折得太早。
- 降本更直接的手段是**减少轮数**：P0-4（轮数预算 + 全新交接，本次数据里续接 30.5M 对比全新 2.6M）、P0-3（浏览器断言，失败 154 次）、P1-2（验证范围）。
- 工作集太大的问题，要从**缩小工作集**入手：文档按预算（P2-1）；任务只给本页面需要的章节；样式和组件规模。

**复现**：scratchpad 下的 `folds.py`（第一次折叠时间）、`sim.py`（时间窗口）、`sim2.py`（读回即保留）。输入是 b4.db 导出的 `calls.json`、`work.json`、`rbytes.json`。
