## 3. 问题根因

分四类：**A. 平台缺陷**；**B. 规则与提示词**；**C. 纯模型错误**；**D. 环境**。

### A. 平台缺陷

#### A1. 登记命令的“已验证”只在任务快照里成立（P0，第一次返工，你的第 1 点）

**现象**：init#1 登记了 4 条命令和 `api` 服务，全部是 `.venv/bin/python …`、`cwd="."`，平台都标为 `verified`。交付合并后平台在项目根跑迁移：

> 项目根目录下找不到启动命令 .venv/bin/python；它可能只存在于任务快照里（依赖和虚拟环境不随交付合并），需要让项目能在根目录安装和启动。

**根因**：
1. `collaboration_register_command` 的 `verified` = “这个任务已经在自己的快照里成功跑过同样的 argv”（`tools.py:392` 的 `command_ran`）。快照里有任务自己建的 `.venv`，项目根没有，所以“验证过”不代表合并后能跑。
2. 根目录要能跑，`prepare_root`（`processes.py:435`）得在**命令的 cwd** 找到依赖清单才会安装。init#1 的清单在 `backend/requirements.txt`，命令 cwd 是项目根，`inspect_environment(root)` 的 runtimes 为空，什么都不装，最后报找不到可执行文件。
3. 两件事平台在登记时都能判断（argv[0] 落在 `.venv/` 这种不合并的目录里；cwd 下没有对应清单），但没有判断，等到合并后才失败，成本是一整次返工（2.10M）。

**这一点 Blog5 的 P1-2 已经提过**（“登记命令时……按清单所在目录建环境，并用登记的命令验证一次”），没有实施。

#### A2. 任务快照嵌在项目根下面，根目录一有 `pyproject.toml`，快照里的 `uv` / `pytest` 就全部失败（P0，你的第 1 点：暂停时还没修好）

**现象**：从 15:48:07 init#2 的交付合并起，任何快照里的 `uv run` / `uv sync` / `uv pip -r pyproject.toml` 都报：

```
error: failed to read from file `/Users/yefenghua/Codes/Agent Test Workspace/Blog9/pyproject.toml`: Operation not permitted (os error 1)
```

init#3 被它卡了 10 分钟（7 次失败），登录任务的 `uv run` 和 `pytest` 也被卡。

**根因**：
1. 快照位置是 `<项目根>/.wdrunge-runs/<实例>/work`（`workspaces.py:161`）。
2. `uv` 找到 `work/pyproject.toml` 后还会**继续向上**找工作区根；`pytest` 确定 rootdir 时也会向上读祖先目录的 `pyproject.toml`。
3. 沙箱规则（`sandbox.py`）是：`(allow file-read-metadata)` 对所有路径；`file-read*` 只给运行时目录和本快照。于是父目录的 `pyproject.toml` **能看到存在、不能读**，工具直接报错退出。根目录没有这个文件时（init#2 期间），`stat` 返回“不存在”，工具就继续，所以第一次没出现。

**复现**（不调用模型，用平台自己的 `sandbox.command_line` + `clean_environment`，同一个快照只差根目录有没有 `pyproject.toml`）：

```
root WITHOUT pyproject: exit 0  Resolved 1 package in 0.82ms
root WITH pyproject:    exit 2  error: failed to read from file `…/Proj/pyproject.toml`: Operation not permitted (os error 1)
```

**为什么暂停时没修好**：这是模型修不了的问题。平台的回执只说“检查沙箱 / 网络边界，不要绕过隔离”，没说被拒的是快照**外面**的父目录文件。模型能做的只有绕开 `uv`：
- init#3 退回到 `uv venv .venv` + `uv pip install --no-config` + 手写 12 个版本号，不再走 `uv.lock`，命令又变成 `.venv/bin/python …`，和第一次返工的做法一样；
- 登录任务往要交付的 `pyproject.toml` 里加了 `[tool.pytest.ini_options]`，只为了让 pytest 不再向上找，这是为平台缺陷改项目代码。

**影响面**：不止 Python。凡是向上查找配置或依赖的工具都会受影响：npm / pnpm 的 workspace、Node 的 `node_modules` 解析、`tsconfig` 的 `extends`、ESLint / Prettier 配置、Cargo workspace、Poetry。前端交付合并之后，前端快照里很可能出现同样的问题。

#### A3. 两个后端会话同时改同一个后端（P0，你的第 2 点）

**先说清楚“同一个工作区”指什么**：两个会话的**文件**是隔离的（init#2 在 `fbf86753`、init#3 在 `8cd1de4a`、登录在 `17e8abb8`，每条命令的 cwd 都能对上）。冲突发生在三样**共享的运行状态**上，加上它们改的是同一套后端代码。下面四个原因缺一个都不会出事。

**① 依赖在“待验收”时就放行，退回时不收回**

**② 共享的运行状态：一个数据库、一个服务名**

## 9. 回答你的两个问题

**Python 虚拟环境为什么导致返工、暂停时为什么还没解决**：
1. 第一次返工：平台把“在快照里跑通过”当成“已验证”，没检查命令依赖的 `.venv` 不会合并、cwd 下也没有可供根目录安装的清单（A1）。

3. 但根目录有了 `pyproject.toml` 以后，嵌在根目录下面的每个快照里，`uv` 和 `pytest` 向上读它都被沙箱拒绝（A2，已复现）。这让第 3 次返工和登录任务都只能绕开 `uv`，绕的方式又回到了第一次返工的老路。这个问题不改平台就修不好。

**为什么两个会话同时改同一个后端**：
1. 依赖在待验收时就放行，退回时不收回；同一角色允许 2 个并行任务（A3①）。

3. 替换服务的保护只覆盖从项目根运行的服务；迁移失败让 `api` 一直留在快照里（A3③）。
