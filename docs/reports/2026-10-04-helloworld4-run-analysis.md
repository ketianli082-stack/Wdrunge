## 3. 问题根因

共 83 次工具调用，失败 1 次（前端）。这次没有大的绕行，主要问题是**一个端口归属的平台缺陷**和**几处小的无效调用**。

### A. 平台缺陷

#### A1. 进程日志里出现的端口被算成这个进程的端口（P1）

- `served_ports()`（`development.py:64`）会把“进程日志里打印过、并且现在能连上”的端口都加到 `job.ports`。web 启动时打印 `web listening on http://127.0.0.1:8101 (proxying /api -> http://127.0.0.1:8100)`，8100 是 api 在监听，能连上，于是 **web 被记成同时占用 8100 和 8101**。证据：测试 06:34:46 的 `manage_process list` 里 web 的 `ports: [8100, 8101]`；前端两次探测实例也是 `ports: [8100, 8199]`。
- 连带后果：
  1. **api 的运行状态指向 web 的进程。** `service_job(name, port)` 按“最新的进程优先”找第一个满足“名字相同**或**端口包含”的进程。web 比 api 新，又“包含”8100，所以查 api 时返回的是 web。Leader 的 `complete_goal` 证据里写 api“running=yes（进程 5fc3e510…）”，web“同一进程 5fc3e510…”，Leader 没有发现这里不对。如果有人 `manage_process stop api`，按同样的查找逻辑会停掉 web。
  2. **把 web 移到项目根时停机时间变长，测试看到 “stopped”。** `relaunch()` 的 `release()` 会等旧进程的所有端口都释放，8100 一直被 api 占着，要等满约 5 秒（20 × 0.25 秒）；新进程的 `service` 字段又是在 `start()` 返回后才赋值。这段时间里 `service_runtime()` 找不到 web，端口也还没开，就报 `stopped`。测试 06:31:17 的 `detect_environment` 正好落在这个窗口里（审核放行在 06:31:14.6）。
  3. **测试据此在自己的快照里重启 web，把项目根那份替换掉了**（06:32:23，`replaced_process: 6c1e0dd…`）。之后验证的是测试快照里的副本；测试交付时（06:35:22）平台再把它移回项目根。这次快照内容和项目根相同，所以结果没出错，但多了 1 次启动、2 次审核、2 次服务切换。
  4. `register_observed()` 对 8100 调用 `observe_service()`，把 api 标成“已验证”，验证人记成了启动 web 的人（注册表里 api 的 `verified_by: testing`、`verified_at` 正好是测试启动 web 的时刻）。如果 8100 当时没登记，还会多出一个叫 web 的假服务。
- 修复：
  1. `served_ports()` 只认这个进程**自己**监听的端口：`ready_port`、启动前空闲的 argv 端口；日志里的端口要排除启动前就已能连上的，或者用 `lsof -p <pid>` / psutil 按 pid 确认；
  2. `service_job()` 先按名字匹配，没有再按端口匹配（分两轮查找）；
  3. `relaunch()` 只等旧进程自己监听的端口；在新进程被标好 `service` 之前，运行状态保持 “being restarted from the project root”（`job.relaunch='pending'` 已经有这个文案，只是旧进程停掉后就看不到了）；
  4. 调度器可以等 `relaunch_delivered()` 完成后再派发依赖它的任务，避免下游拿到中间状态。

#### A2. 从快照启动同名服务会替换项目根的副本（P2）

- `keep_running=true` 的“替换正在运行的副本”不区分工作区。测试在自己的快照里启动 web，直接替换掉了项目根那份已交付的 web。
- 这次是 A1 引出的（测试以为 web 停了），快照内容也和项目根一致。但一般情况下，这意味着任何任务都能悄悄把用户正在用的服务换成一份还没合并的代码。
- 修复：项目根已经有同名保留服务在跑时，快照里的同名启动应拒绝并提示“已在项目根运行，直接使用”；确实要测试未交付的改动，按提示词另起一个新登记的端口。

#### A3. 任何一次发布都会重启 `cwd='.'` 的保留服务（P2）

- `changed_paths()` 在服务 `cwd` 是 `.` 时，把项目里任何文件的变化都算作“和它有关”。api 的启动命令是 `python3 backend/app.py 8100`、`cwd='.'`，所以前端发布（只改了 `frontend/`）和测试发布（只改了 `README.md` 和 `docs/`）各让 api 重启了一次（06:31:14、06:35:25）。
- 每次重启都要调用一次审核模型，服务也会断开约 1 秒。重启 06:31:14 那次刚好和 A1 的窗口重叠。
- 修复：`cwd='.'` 时，用启动命令里脚本所在的目录（这里是 `backend/`）作为范围；或者至少跳过 `docs/`、`*.md` 这类不会被服务加载的文件。

#### A4. 临时探测进程会被自动登记进服务注册表（P2）

- 前端用 `name="web-failure-probe"` 起了一个 8199 的探测实例（没开 `keep_running`）。`register_observed()` 把它自动登记成了一个 `verified` 的服务，前端只好再调一次 `collaboration_register_service(remove=true)` 删掉。
- 修复：只自动登记有 `keep_running`、或者端口已在注册表中的进程；或者把自动登记的服务标成“仅本任务”，任务结束时一起清掉。

#### A5. 登记服务时，命令里的端口和分配的端口不一致也能通过（P3）

- 后端第一次登记时命令写的是 `8099`，注册表分配的是 `8100`，登记成功；后端自己发现后又登记了一次。可以在登记时检查 argv 里的数字端口是否等于分配的端口，不一致就提示。

## 10. 改进建议（按收益排序；均未实施，需要你批准）

| 优先级 | 改动 | 预期收益 |
| --- | --- | --- |
| P1 | `served_ports()` 只认进程自己监听的端口（`ready_port`、启动前空闲的 argv 端口；日志端口排除启动前已可连接的，或按 pid 确认）；`service_job()` 先按名字再按端口；`relaunch()` 只等自己的端口，新进程标好 `service` 前运行状态保持 “being restarted” | 服务状态、进程 ID、`manage_process stop/logs` 都指向正确的进程；搬迁停机从约 5 秒降到约 1 秒；下游不会看到 “stopped” |
| P1 | 调度器在 `relaunch_delivered()` 完成后再派发依赖它的任务（或下游的服务状态显示“正在从项目根重启，稍候”） | 测试不再自行重启服务 |
| P2 | 项目根已有同名保留服务在跑时，拒绝快照里的同名 `keep_running` 启动，提示直接使用 | 防止已交付的服务被换成未合并的副本 |
| P2 | `refresh_after_publish()`：`cwd='.'` 时用启动脚本所在目录作为范围，或跳过 `docs/`、`*.md` | 少 2 次无谓重启和 2 次审核调用 |
| P2 | `register_observed()` 不自动登记没开 `keep_running` 的临时进程；不替别的服务标“已验证” | 不再需要手动删除探测服务；注册表的验证记录可信 |
| P2 | Leader 提示词：“最简”的全栈目标优先单进程（后端同时提供页面和接口）；不暗示代理/CDN/静态服务器等实现；同源方案不加跨域验收项；最终答复不列团队花名册、不提注册表 | 去掉 Node 运行时和代理；前端约 −5 次调用；README 更短 |
| P2 | 交付检查恢复**精确标识符**检查：`leader:<key>` 形式的任务 ID、32 位十六进制进程 ID、工具名（`browser_verify`、`manage_process`、`keep_running`…）、“注册表/registry” | 6.2 节的泄漏都能在交付时拦截，几乎不会误报 |
| P2 | `collaboration_read` 接受路径，或者在 “document not found” 里提示“这是路径，请先 catalog 拿 ID” | 消除本次唯一的工具失败 |
| P3 | `collaboration_register_service` 检查 argv 里的端口是否等于分配的端口 | 少 1 次重新登记 |
| P3 | 查 uvicorn 日志里的 “Could not record reviewer usage” / “No store to record”，修复 worker 上下文里的审核记账 | 审核成本完整可见（本次约 6 万 token 没记上） |
| P3 | small 目标配置 `WDRUNGE_MODEL_SMALL_TASKS` | 调用数已近下限，这是下一步降成本的最大杠杆 |
| P3 | `detect_environment` 标注 “anaconda base 带预装包”，或优先项目 `.venv` / Homebrew python | 可复现性 |

**预期**：本次已经达到之前设定的合理基线（约 1.0M token、15 分钟级）。落实 P1 后主要提升的是**正确性**（服务状态可信、不出现服务被替换），token 大约再省 0.03～0.05M。再落实 P2 里的 Leader 提示词改动（单进程方案），同样的 Hello World 大约 **50～55 次调用、0.85～0.95M、约 12～14 分钟**。之后的主要杠杆是模型单价，而不是调用数。

另外要注意：这次是第一次“干净”的运行，样本只有一次。Leader 把契约内联、后端先于前端交付，这个顺序让 STALE 和草稿相关的修复都没被走到。建议再跑一次“后端契约以文档形式先发布、前端先于后端交付”的场景，用来验证 3.A2（HW3）的修复。
