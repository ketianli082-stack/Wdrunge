## 3. 问题根因

共 147 次工具调用，失败 5 次（Leader 1、后端 1、前端 2、测试 1）。另有若干**“成功但无效”**的调用（3.D）和**不是失败、但浪费最大**的平台缺陷（3.A1）。

### A. 平台缺陷

#### A1. 保留服务跑在任务快照里，别人看不到自己的文件（本次最大的浪费）

- 每个 worker 在 `.wdrunge-runs/<id>/work` 快照里工作。后端用 `keep_running=true` 启动的 web 进程，`cwd` 是**后端的快照**；`backend/app.py` 按 `__file__` 解析静态根，于是 web 服务的静态根 = 后端快照下的 `frontend/`。
- 前端在**自己的快照**里写 `frontend/index.html`，运行中的 8100 永远看不到它；前端提交合并到项目根之后，8100 依然看不到（进程还在后端快照里）。`processes.mark_stale()` 能把服务标成 STALE，但**只在合并时标记、不会重启**，而且对“前端在工作期间看不到自己的文件”这种情况无能为力。
- Leader 的前端任务写着“直接在运行中的服务上打开 http://127.0.0.1:8100/ 验证渲染结果；不要重启或另起后端服务”——**在快照隔离下这是做不到的要求**。前端连续撞上：
  - 11:55:59 看到的是后端的占位页（200）；
  - 11:59 之后占位页被后端删掉，变成 404；
  - 10 次调用排查（含一次越权 `ls` 另一个快照，被沙箱拒绝）；
  - 最后自建同源代理和 3 个故障注入服务完成自测（36 次工具调用）。
- 连锁影响：Leader 多一轮诊断和一条 1.5K 字的指令；测试必须重启服务；**README 里写进了一句错误的话**（6.2）；最终交给用户的 8100 服务跑在**测试的快照** `.wdrunge-runs/005d…/work` 里（PID 85144，仍在运行，4 小时后到期）——用户此刻改项目根下的 `frontend/index.html`，页面不会变；如果清理快照，服务会直接失效。
- 量化：前端 B、C 两段（11:59–12:09）24 次模型调用、约 **0.60M token、10 分钟**；加上 Leader 和测试的连带，合计约 0.65M（占本次 31%）。

#### A2. `/tmp` 不可写，但环境说明里没有

- 沙箱只允许写工作区和 scratch（`TMPDIR` 已指向 scratch），`/tmp` 不可写。`detect_environment.host.notes` 列了 BSD/GNU 差异，却没有这一条。
- 前端 `curl -o /tmp/vue.global.prod.js` 失败（exit 23）；测试在 `sh -c` 里 `curl -o /tmp/root.html`，**整体 exit 0 被记为成功**，但其中两项检查实际没有执行，测试读完输出后又重跑一次写到 `docs/testing/`。
- 建议：host notes 增加“/tmp 不可写，临时文件用 `$TMPDIR`”。

#### A3. 沙箱里的 `python3` 是 Wdrunge 自己的 venv

- `detect_environment` 返回 `"python3": "/Users/yefenghua/Codes/Wdrunge/backend/.venv/bin/python3"`；当前运行中的 8100 进程也是 `/Users/yefenghua/Codes/Wdrunge/backend/.venv/bin/python3 backend/app.py`。
- 原因：`sandbox.py:clean_environment()` 原样继承了后端进程的 `PATH`，而后端是在自己的 venv 里启动的；`command_line()` 又把 `sys.prefix` 加进可读路径。
- 风险：用户项目在一个装有 fastapi、langgraph、pydantic 等依赖的解释器下运行和验收。本次后端只用标准库所以没出事；但任何一个“忘了写进依赖清单”的 import 都会在这里通过、在用户机器上失败——**这直接破坏“可复现”这个验收前提**。
- 建议：构造 `PATH` 时去掉 `sys.prefix/bin`（以及 `VIRTUAL_ENV`），优先用项目 `.venv`，否则用系统 / Homebrew 的 python3。

#### A4. 审核模型不认识“本任务自己创建的文件”

- 后端删除自己 3 分钟前写的 `frontend/index.html`、`frontend/assets/` 时，审核模型（qwen-flash）以“任务要求不要改动 frontend/”为由转人工，置信度 0.8～0.9。两次人工审批共等待约 1.5 分钟。
- 这两个文件不在快照的 base manifest 里（`manifest.json` 只有 `docs/api-contract.md`），平台完全可以判断“这是本任务新建的文件”，直接放行，不需要模型判断。
- 当然，根源是后端越界在 `frontend/` 下放占位文件（5 节）。

## 9. 其他影响建站效率的因素

1. **保留服务 + 快照隔离的语义冲突**（3.A1）。这是“保留服务”上线后第一次真实运行暴露的问题，影响三个角色和最终交付状态。
2. **`.wdrunge-runs` 不能清理**：三个快照（5MB）仍在项目目录里；而当前 8100 服务正依赖其中的测试快照运行。清理快照和保留服务现在是互相矛盾的，修 A1 时需要一起考虑。
3. **合并范围过宽**：测试声明交付 4 个文件，实际合并了 5 个（多了断言失败的截图）；前端交付了 3 张相同的截图。建议只合并声明的交付物和报告里引用的证据，`browser_verify` 遇到与已有截图哈希相同时复用原路径。
4. **审核模型的上下文**：它只看到“任务说不要改 frontend/”，看不到“这个文件是本任务刚创建的”（3.A4）。
5. **所有调用都用 `qwen3.8-max`**：small goal 的前端/测试完全可以用更便宜的模型（`WDRUNGE_MODEL_SMALL_TASKS` 仍未配置）。

C=ee2e458a-ea04-490e-b1a5-cdd3e22757f2
# 2. 按角色统计 token 与缓存
sqlite3 /path/w.db "select agent_id, count(*), sum(total_tokens), sum(cached_tokens), sum(output_tokens), max(context_tokens)
                    from agent_usage where conversation_id='$C' group by agent_id"
# 3. 全部角色的工具调用（本次 worker 也已写入）
sqlite3 /path/w.db "select agent_id, created_at, tool, status, arguments, result from tool_calls
                    where conversation_id='$C' order by created_at"
# 4. 逐次调用的缓存命中：agent_usage 按 created_at 排序，未命中 = total - output - cached

# 7. Leader 工具列表扩张：以 SimpleNamespace 模拟消息，比较 select_tools('leader', …) 在使用
#    collaboration_inspect_request 前后的结果
