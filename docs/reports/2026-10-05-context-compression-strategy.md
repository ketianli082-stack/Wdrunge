# 上下文压缩策略（方案，2026-10-05）

本文是方案，**没有改代码**。依据：`2026-10-05-context-compression-research.md` 的调研数据、现有实现（`context_fold.py`、`memory.py`、`worker.py`），以及 Claude Code 源码分析里的分层压缩流水线。

---

## 0. 总览

每次模型调用前，按“能不调模型就不调模型、能少丢就少丢”的顺序走一条流水线。前一层的输出是后一层的输入，后一层只在前一层不够时才动手：

| 层 | 名称 | 做什么 | 调模型？ | 丢信息？ | 什么时候做 |
| --- | --- | --- | --- | --- | --- |
| L0 | 入口预算 | 单条结果、单次响应的结果合计按 token 封顶；重复读取返回“内容未变，见消息 X” | 否 | 否（全文可取回） | 工具结果进入上下文时，每次都做 |
| L1 | 历史剪除 | 整条删掉**冗余**的消息：已被取代的结果、后来成功了的失败重试、内容相同的轮询、已确认的提醒 | 否 | 否（有更新的副本或台账） | 与 L2 同一批次 |
| L2 | 微压缩 | 白名单工具（可重新获取的：读文件、读文档、搜索、只读命令等）的旧结果只留元信息；写入调用的大参数换成占位 | 否 | 可重新获取 | 缓存成本规则判定“改得值”时；缓存已失效时 |
| L3 | 上下文折叠 | 把窗口外**已完成的工作段**折叠成一段短摘要，其余保持原样 | 是（小调用） | 段内细节，可 recall | 超过预算 60% 时后台预备，下一次批量改写时一起提交；超过 80% 时立即提交 |
| L4 | 整体压缩 | 整段历史摘要，失败时由平台交接 | 是 | 最多 | 前三层之后仍超预算、上下文溢出报错、模型主动 checkpoint |

你列的四层对应 L1–L4。L0 是新增的前置层：Claude Code 在剪除之前也有一步（`applyToolResultBudget`）。调研中的两个根因，单条结果过大和重复读取，都要在入口解决，后面各层解决不了。

所有改写都遵守三条现有原则：
1. 原件进审计（`save_compaction`），`recall_context(message_id)` 能取回。
2. 不拆开调用和结果。
3. 台账、系统提示、任务输入不参与压缩。

## 1. 前提：缓存决定“什么时候改”

DashScope 没有 Claude 的 `cache_edits`，前缀缓存不能局部删除。**改动历史中的任何一条，从这条往后的缓存就全部失效**。所以 Claude Code 的两条微压缩路径在我们这里要换一种做法：

| Claude Code | 原理 | 我们的等价做法 |
| --- | --- | --- |
| Cached MicroCompact | 用 `cache_edits` 在服务端删除，缓存不失效 | 做不到。改为**缓存成本规则**：只有省下的钱大于缓存失效的代价才改，并且所有层的改动合并成一次提交 |
| Time-based MicroCompact | 距上次助手回复超过阈值时缓存已过期，清理没有代价 | **缓存已失效路径**：间隔 ≥ 10 分钟（实测 DashScope 隐式缓存的分界），或上一次调用命中率 < 20% 时，不需要攒够量就可以改 |

### 1.1 缓存成本规则（取代固定的 12K 阈值）

记号：
- `S`：从第一条被改动的消息到末尾的 token 数。下一次调用这部分无法命中缓存，按全价计费。
- `R`：本次改写省下的 token 数。
- `p`：缓存命中价格比例。隐式缓存约 0.2。
- `n`：这个线程预计还会调用的次数。用已调用次数估计，下限 10，上限 40。
- `C`：本次改写需要的模型调用费用，只有 L3/L4 有。按输入 token 等价折算。

改写**值得**的条件：

```
n · p · R  ≥  (1 − p) · (S − R) + C
```

- **代入当前数据**：p = 0.2，S = 60K，n = 20，C = 0，得到 R ≥ 10K。和现在的 12K 是一个量级，说明 12K 的方向是对的。
- **它比固定值好在哪**：
  - 任务早期 n 小、上下文短时，不急着改；
  - 上下文越长、任务越长，越早改；
  - 缓存已失效时，代价项为 0，有可省的就改（设一个 2K 下限，避免为几十个 token 改写）。
- **改写位置**：S 由最旧的被改动消息决定。所以一次批量改写应**把这一批能改的都改掉**：L1、L2、已预备好的 L3 一起提交，只失效一次。
- **校准**：p 从 `agent_usage` 的实际命中数据持续校准，不写死。

## 2. L0 入口预算

### 2.1 单条结果封顶（根因修复 1）

- **位置**：工具结果进入上下文的唯一入口。Worker 是 `guarded_tools`，Leader 是 `team.py` 里的分发处。不在每个工具里各写一套。
- **单条上限**：`WDRUNGE_RESULT_TOKENS`，默认 **8K 估算 token**。原文层 30K 里至少能同时放下 3 条。
- **单次响应合计上限**：`WDRUNGE_TURN_RESULT_TOKENS`，默认 **20K**。
  - **“单次响应”指什么**：模型的一次回复（一条 AIMessage），加上它发起的工具调用返回的结果。不是整个任务。
  - **长任务也一样**：后端跑一个长任务，是几十到上百次这样的响应。Blog2 单个线程最多 132 次，后端共 219 次模型调用。整个任务的上下文大小由 L2–L4 的分层控制，不由这个上限控制。
  - **它防的是什么**：一次回复里并行发起多个大读取（比如 4 个 8K），一下子把原文层占满。超出时从最大的结果开始缩。
  - **Blog2 实测**（来自压缩审计里的原件，共 1,385 次响应、2,191 条结果）：
    - 每次响应的结果合计：中位数 832，p90 3.9K，p99 11.1K，最大 16.6K。**没有一次超过 20K**。
    - 单条结果：中位数 436，p99 8.9K，最大 16.2K。超过 8K 的有 26 条（1.2%），主要是 `collaboration_read` 14 条、`recall_context` 9 条，都可以分页。
    - 所以 20K 只是兜底，正常不会触发；8K 只影响约 1% 的结果，影响方式是多翻一页。
  - **为什么不放大**：原文层是 30K。单次响应超过 20K，下一次响应基本就挤不进原文层了。
- **超出时怎么处理**：
  - **可分页的读取**（文件、文档章节、recall）：截到上限，返回 `next_offset`。模型按需翻页，和现在的翻页协议一致。
  - **其他输出**：保留开头约 60% 和结尾约 40%，中间写明“省略了多少字符，recall_context(message_id, offset) 可取回”。原文进审计。
- **计量**：按 token（UTF-8 字节/2），不按字符。中文因此不会比英文多占约 3 倍。
- **工具自己的字符上限保留**：比如 30,000 字符，作为第二道保险。

### 2.2 读取去重：按“上一份是否仍是原文”判断（根因修复 2）

- **规则**：同一资源（路径加区间，或文档加章节加版本，或 sha 相同）的上一份副本**仍在原文层**时，返回：

  ```json
  {"unchanged": true, "message_id": "X", "hint": "内容与消息 X 相同，仍在上下文中"}
  ```

  不再重发全文。上一份已经降为摘录、指针或被删时，正常返回全文。
- **判断依据**：上下文里该消息的 `fold.level == 0`，不靠线程级的回执。
- **修 `collaboration_read`**：`ContextMemory.record()` 不再在每次压缩时把整个线程的 `read_context` 重置掉。改为只作废**这次被改动的消息**对应的回执。
- **`read_project_file` 也接入同一机制**：Blog2 里有 53 次读取，参数和内容与之前完全相同。
- **模型确实需要重读时**（比如怀疑文件被别人改了）：`force=true`。sha 变了会自然返回全文。

## 3. L1 历史剪除

**定义**：整条删除**冗余**消息，不做摘要，也不留指针。

**冗余的判定标准**：删掉这条消息后，模型能从上下文里剩下的内容得到同样的信息。剩下的内容指同一目标更新的结果、台账，或者后面的结果。只要有一点信息只在这条消息里，它就不算冗余。

我**不建议**照搬“超预算就从最旧的整轮开始删”的做法。那样删掉的不全是冗余内容，又不留痕，就是丢信息。这种情况应该交给 L3 折叠。

### 3.1 算冗余的（都是通用规则，不针对某个工具或角色）

| 类型 | 判定 | 为什么信息没丢 | 例子 |
| --- | --- | --- | --- |
| 完全重复 | 同一工具、同一参数，后面又调用了一次，结果逐字相同 | 后面那份一模一样 | 同一章节读了两遍，内容没变；轮询状态，返回没变 |
| 被取代 | 同一目标（同一文件的全文、同一文档章节、同一进程、同一检查）后来有更新的成功结果 | 更新的那份就是现状 | 文档 v2 的章节，后来读了 v3 |
| 已过时 | 读过的文件后来被自己改写了 | 文件现状在磁盘上，自己写了什么在写入记录和台账里 | 读了 `app.py`，然后整体重写了 |
| 瞬时失败的重试 | **同一参数**的调用失败后，又重试成功了 | 成功的那次就是结果；失败原因不影响后续 | 网络超时后重试同一命令成功 |
| 已确认的提醒 | 运行时打了“可重发”标记的提醒，模型已经看过；旧的目标提醒 | 运行时需要时会重新下发 | 收件箱提醒、目标状态提醒 |
| 整次响应 | 一次响应的所有结果都属于上面几类，并且模型这次回复没有正文 | 连同调用一起删，不拆开调用和结果 | 一次只读了一个后来又重读的章节 |

### 3.2 不算冗余的（不删，超预算时交给 L2 或 L3）

| 情况 | 为什么 |
| --- | --- |
| 同一文件的不同区间、不同分页 | 内容互补，不是重复 |
| 失败后换了参数或换了做法才成功 | 失败原因解释了为什么换做法，模型需要知道哪条路走不通 |
| 还没解决的失败 | 台账里仍是“未关闭”，删了会让模型以为没问题 |
| 模型自己的正文 | 那是它的判断和计划，交给 L3 摘要 |
| 用户和任务输入、摘要、台账 | 不参与压缩 |
| 原文层里的任何内容 | 最近的内容一律不动 |

删除的消息原件进审计，按消息 ID 仍可 recall。

### 3.3 Blog2 里有多少冗余

按上面的规则粗算，数据来自 `tool_calls`，不含 Leader，共 729 条结果、约 100 万估算 token：

| 类型 | 条数 | 估算 token |
| --- | --- | --- |
| 完全重复 | 83（`collaboration_read` 60，`read_project_file` 19） | 11.7 万 |
| 被取代 | 59（`collaboration_read` 48） | 14.4 万 |
| 瞬时失败的重试 | 12 | 0.6 万 |
| **合计** | **154（21%）** | **26.7 万（27%）** |

说明：
- 这张表的“完全重复”比调研报告里的 53 次多，是因为判定更宽：参数规范化后再比较，并且与后面任意一次相同就算，而不只和上一次比。
- “瞬时失败的重试”这里用了较宽的判定：失败后 3 次调用内同一工具成功。方案里用严格判定（同一参数），实际会更少。
- `tool_calls` 的结果存储时截到了 8,000 字符，所以 token 数偏低。
- 每条冗余结果，在被删之前会随每一次调用重复发送。

这也说明 L0 的读取去重和 L1 是一体的两面：
- **去重**让重复内容不进上下文；
- **剪除**清理已经进来的。

## 4. L2 微压缩

### 4.1 白名单：按“结果能否重新获取”声明，不写死工具名

- **怎么声明**：工具注册时声明 `context_policy`：
  - `recomputable`：结果可以重新获取。读文件、列目录、搜索、读文档或大纲、recall、进程日志、网页、只读命令（复用 `progress.read_only_call` 的判断）。
  - `durable`：结果承载状态或决定，不能丢细节。发布回执、状态流转、任务检查结果、审核意见、checkpoint。
  - 默认 `durable`。新工具不声明就不会被误压。
- **写入类调用的大参数**（文件内容、文档正文）：换成 `<N characters written to path; the file is on disk>`。现在已经这样做，并已防止重复包装。

### 4.2 分层（保持已批准的 30K / 15K）

| 区域（从新到旧，按原件 token 计） | `recomputable` 结果 | `durable` 结果 |
| --- | --- | --- |
| 原文层：最近 30K | 原样 | 原样 |
| 摘录层：再往前 15K | 元信息 + 开头 600 字符 | 原样 |
| 更早 | 一行元信息：路径/区间/sha/字符数/next_offset/退出码 + 消息 ID | 原样，交给 L3 |

**例外**：每份文档最新的大纲在任何层都保留章节 ID（现状）。

### 4.3 超大轮次的分层修正（根因修复 3）

- **按单条结果放进原文层**：一轮放不进原文层时，从新到旧尽量保留结果原文，其余降为摘录。不再整轮直接降为指针。
- **继续往前累计**：遇到这样的轮次时跳过它，不在它这里停下。
- 有了 L0 之后这种情况会很少，但规则要对。

### 4.4 时机

两条路径，见 1.1：
- **缓存未失效**：按成本规则判定值得时，和 L1、L3 合并提交。
- **缓存已失效**：直接做，不需要攒够量。

## 5. L3 上下文折叠

**定义**：选择性折叠。原文层之外、**已经完成的工作段**折叠成一段摘要；其他段落保持原样。

### 5.1 怎么切段

- **按通用的里程碑切**，不按固定轮数：
  - 一次成功的持久化动作：写文件、发布、状态流转、写工作日志；
  - 一次 checkpoint；
  - 一条新的用户或任务输入。
- **段的范围**：两个里程碑之间的一段轮次就是一段。
- **可折叠的段**：整段都在原文层之外，并且段内的失败都已关闭。

### 5.2 摘要的内容

每段约 150–400 token，包括：
- 做了什么、结论；
- 改了哪些文件或文档（路径、ID）；
- 段内被放弃的方案及原因；
- 消息 ID 范围，`recall_context` 可取回。

台账已有的事实不重复。模型用 `qwen3.7-plus`，关闭思考。输入只有这一段，所以很便宜。

### 5.3 时机：后台预备，批量提交

| 状态 | 动作 |
| --- | --- |
| L1+L2 之后 > 预算 60%（约 54K） | **后台**为最旧的可折叠段生成摘要，不阻塞当前调用。段是历史，内容不会再变，摘要一直有效 |
| 下一次 L1/L2 批量改写，或缓存已失效 | 把已预备好的段一起提交，只失效一次缓存 |
| > 预算 80%（约 72K） | 立即提交；还没预备好的段同步生成 |
| 摘要失败 | 这一段不折叠，交给 L4；不重试成死循环 |

### 5.4 替换式还是投影式

Claude Code 的折叠是“读取时投影”：原件留在会话里，每次调用时才把折叠应用上去。

我建议**沿用替换 + 审计**，不做投影。原因是 LangGraph 每一步都会把整个消息列表写进 checkpoint，投影式会让 checkpoint 一直按完整历史增长。审计加 recall 已经提供了同样的可恢复性。

## 6. L4 整体压缩

保留现有流程（`qwen3.7-plus` 摘要，失败时平台交接），并做两处修正：

1. **摘要流程不截断原文层**：现在会把所有工具结果截到 3,000 字符，包括最新一轮。改为只截要被摘要的部分；原文层原样保留，放不下时才按 L0 的规则缩。
2. **L3 的段摘要直接并入**：整体摘要的输入是“段摘要 + 未折叠的部分”，不重新从原件摘要，因此更短、更便宜。

**触发条件**（任一）：
- L1–L3 之后仍超预算（约 90K）；
- 上下文溢出报错；
- 模型主动调用 `checkpoint_context`；
- 连续只读 24 轮（现有的进度检测）。

**熔断**：摘要失败一次（含一次目标减半的重试）就直接进入平台交接，不反复重试（现状）。

## 7. 阈值汇总

预算 B = 窗口 131,072 × 0.75 − 工具 schema ≈ 85K–90K。

| 参数 | 默认值 | 依据 |
| --- | --- | --- |
| 单条结果上限 | 8K | 原文层能放 3 条；Codex 16K、OpenCode 50KB 是同一量级 |
| 单次响应的结果合计 | 20K | 当前响应放得进原文层，并给下一次留空间；Blog2 最大 16.6K，从未触发 |
| 原文层 | 30K | 已批准；覆盖率拐点（62%） |
| 摘录层 | 15K | 已批准 |
| 缓存已失效的判定 | 间隔 ≥ 10 分钟，或上次命中率 < 20% | 实测数据（调研 3.1） |
| 改写门槛 | 缓存成本规则，p = 0.2，n ∈ [10, 40] | 代入当前数据约 10K，与现在的 12K 一致 |
| L3 预备 / 立即提交 | 0.6B / 0.8B | 参照 Claude Code 90% 预备、95% 阻塞，但我们的预算本身已经留了 25% 余量 |
| L4 | > B | 现状 |

全部阈值都可以通过环境变量调整，按 token 计。

## 8. 实施顺序与验证

按“根因优先、风险由低到高”排序：

| 阶段 | 内容 | 预期 | 验证 |
| --- | --- | --- | --- |
| 1 | L0（单条与单次响应封顶、读取去重、回执修复）+ 4.3 分层修正 | 去掉超大结果和“内容还在却重读”这两个根因 | 用 Blog2 的 `tool_calls` 重放：重复读取次数、单次上下文大小 |
| 2 | L1 + L2 白名单（`context_policy`）+ 缓存成本规则 + 缓存已失效路径 | 改写次数减少、每次改写更值 | 重放统计缓存失效次数和计费等价 token；对比现在的 12K 固定阈值 |
| 3 | L3 后台预备、批量提交 | 长任务的上下文稳定在 0.6B 以下 | 重放 + 真实运行一个长任务 |
| 4 | L4 两处修正 | 摘要更短，最新一轮不再被截断 | 单元测试 + 真实调用一次摘要 |

每个阶段做完都用重放量化，最后跑 Blog3 做端到端对比（总 token、命中率、重读次数、任务完成情况）。

## 9. 需要你决定的

1. **单条结果上限**：8K 还是更大（比如 12K）。更大意味着翻页更少，但原文层能同时放下的结果更少。
2. **L1 是否只删冗余内容**（判定标准见 3.1、3.2）：我的建议是是。你图里的“历史剪除”如果指的是超预算时直接删最旧的轮次，那会丢信息；我建议这种情况交给 L3。
3. **L3 后台预备**：需要异步任务管理，实现复杂度最高。也可以先做同步版本：在批量改写时同步生成段摘要，后面再改成异步。
4. **白名单的声明方式**：在工具上声明 `context_policy`（建议），还是集中写一张表。
5. **实施顺序**：是否按第 8 节的顺序推进。

## 10. 实施记录（2026-10-05）

按本方案实现，第 9 节的待决事项都按建议执行：
- 单条上限 8K；
- L1 只删冗余内容；
- L3 直接做后台预备；
- 白名单在工具上声明；
- 按第 8 节的顺序推进。

### 10.1 与方案不同的地方

| 方案 | 实际 | 原因 |
| --- | --- | --- |
| 1.1 改写门槛：`n·p·R ≥ (1−p)(S−R)`，n 用已调用次数估计 | **rent-or-buy**：等待累计多付的 p·R 达到一次改写的代价 (1−p)·S 时才改写 | 第一版重放发现，原规则拿“现在改”和“永远不改”比，没考虑“攒一攒再改”。它让改写过于频繁：后端 66 次折叠加 17 次段摘要，按缓存计价反而比旧做法贵 20%。rent-or-buy 是这类问题的标准在线规则，最坏不超过事后最优的两倍，也不再需要估计“还剩几次调用” |
| 1 缓存已失效：间隔 ≥ 10 分钟，**或上次命中率 < 20%** | 只看间隔 | 上次命中率低，通常只说明上次刚改写过；那次调用已经建好新缓存，下一次照样命中。按命中率判断会让改写一次接一次 |
| 5.3 超过 80% 立即提交 | 超过 80% **且这次改写能降到 60% 以下**才立即提交 | 后端折叠到底之后，上下文的下限本身就接近 80%。无条件立即提交会让每次调用都改一点，重放中后端改写 46 次、成本比旧做法还高 |
| 3.1 已确认的提醒可删 | 只删被新提醒取代的目标提醒和已结束的只读计数提示；**收件箱提醒不删** | 收件箱提醒里是同事的消息，确认之后运行时不会重发，删了就丢信息；它们在 L3 随所在的工作段一起摘要 |
| 2.2 读取去重返回“见消息 X” | 返回 `unchanged` 通知，说明“同一参数的结果仍在上文”；紧接着再调用一次或 `force=true` 返回全文 | 模型看不到消息 ID，“见消息 X”没法用 |
| 2.1 单条/单次响应上限固定 | 窗口较小时不超过预算的 1/4、1/3 | 小窗口模型下 8K 可能超过整个预算 |
| 5.1 段内的失败都已关闭才可折叠 | 去掉这个条件 | 重放发现后端有 9 个失败一直没有“同一调用成功”来关闭（后来换了参数才成功），它们所在的段永远折叠不掉，改写之后剩下的上下文从 52K 一路涨到 78K。台账本来就原样列出未解决的失败和对应消息 ID，不需要靠留住整段来保留 |

### 10.2 代码

- `app/agents/context_policy.py`（新）：压缩策略注册；`@tool(context_policy=...)` 声明；未声明的默认 durable。
- `app/agents/context_fold.py`：
  - L0：`ingest`、`cap_result`、`unchanged_notice`；
  - L1：`supersession` 新增“同一调用相同结果”和“失败后成功”两条规则，以及 `prune`；

  - L3：`segments`。

  - `prepare` 依次处理 L0～L3，再按 rent-or-buy 决定是否提交；

  - `summarize_history` 实现 L4，不再截断原文层；
  - 新增 `cache_cold`。
- `app/agents/resilience.py`：每次响应记录请求时间 `wdrunge_requested_at`。

### 10.4 局限与后续

1. **改写之后的下限仍在缓慢上升**：后端从 52K 升到约 67K，前端从 47K 升到约 70K。主要来自不断累积的段摘要；重放用的假摘要每条约 480 token，真实摘要约 200 token，实际会低一些。下一步可以在段摘要累计超过一定量时，把最旧的几条合并成一条。
2. **重放的局限**：
   - 历史是按调用时间重建的，模型正文为空；
   - 约 20% 的结果只有截到 8,000 字符的版本；
   - 段摘要用的是假模型；
   - 与旧做法的对比是近似。
   
   结论需要 Blog3 端到端确认。
3. **默认值的依据**：`WDRUNGE_CACHE_HIT_PRICE=0.2` 和 `WDRUNGE_CACHE_COLD_SECONDS=600` 来自阿里云文档和本地数据，样本不多，建议用 Blog3 的 `agent_usage` 校准。
