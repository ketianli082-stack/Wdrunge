## 3. 问题根因

分四类：
- **A. 平台缺陷**：机制做错了，换模型也会出问题。
- **B. 规则与提示词**：机制没错，但给模型的约束或引导不够。
- **C. 纯模型错误**。
- **D. 环境**。

### A. 平台缺陷

#### A1. 提交“先合并、后校验”，校验失败后再也合并不进去（P0）

**代码路径**：`collaboration/tools.py:307-322`（transition）→ `service.publish_artifacts` → `service.transition`。

1. `submit_task` 先调 `publish_artifacts`。它只检查**任务声明的** artifacts（这里是空列表），然后把快照合并进根目录，设 `workspace_published=True`。
2. 接着调 `transition`。它才检查**本次提交列出的** artifacts，而且是在**根目录**（`p['workspace_path']`）里查。
3. 05:14:54 提交里列了 `.task-scratch/*.py`。scratch 不参与合并，所以第 2 步报“不存在”，提交被拒。但第 1 步已经合并完了。
4. 之后 `publish_artifacts` 看到 `workspace_published=True` 就直接返回，不再合并。第 2 步却一直查根目录。所以快照里新建的 `backend/scripts/verify_contract.py` 永远“不存在”（项目根目录 `backend/scripts/` 下至今只有 `export_openapi.py`）。
5. 错误提示只说“Artifact does not exist”，没说“在项目根目录里查”“快照改动已不再合并”。模型只能在快照里删、移、改名。

**连带后果**：
- 租约过期后，调度器看到 `workspace_published=True`，按设计分配**新工作区**，`resume` 也被关掉（`service.py:763-767`）。所以后端第二轮是全新上下文，快照里没合并的工作全部丢失（A4）。
- 根目录被合并了一个**未被接受**的版本。

#### A2. 平台自己的命令走 AI 审核和用户审批，失败时原因丢失（P0）

**代码路径**：`publish_artifacts` → `_migrate_then_refresh` → `apply_migration` → `processes.prepare_root` → `installation_commands`。

1. 合并的路径里有 `backend/requirements.txt`，快照里有 `backend/.venv`，根目录没有，于是 `prepare_root` 决定在根目录安装依赖。
2. `installation_commands` 生成 `[sys.executable, '-m', 'venv', …/Blog3/backend/.venv]`。`sys.executable` 是 **Wdrunge 平台自己**的 `backend/.venv/bin/python3`。
3. 这条命令以 `agent=backend` 的名义进了 `permissions().authorize`。AI 审核的理由是“试图在项目外路径创建虚拟环境，与当前任务无关”，转为用户审批。没人批，10 分钟后过期（05:14:57 → 05:24:57）。
4. `apply_migration` 收到空输出，发出事件“迁移命令 … migrate.py 在项目根目录执行失败”。事件里**没有失败原因（等待审批过期）、没有 cwd、没有 timed_out**。
5. Leader 据此判断“migrate.py 位于 backend/，从根目录执行就会失败”，要求后端改路径解析。后端写了根目录 `migrate.py` 转发，把登记的 cwd 从 `backend` 改成 `.`。**这些都是在修一个不存在的问题。**

**另外两个问题**：
- 登记的迁移命令用的是数据目录里的绝对路径解释器（`.wdrunge-data/blog-api-venv/bin/python`），根本不需要根目录 `.venv`。只要快照里有 `.venv` 就安装，这个判断（`had_own`）太宽。
- 平台发起的操作被记在 agent 名下，审核又是按 agent 的任务来判断“相关性”，天然会误判。

#### A3. 实现任务读自己代码的循环（P0）

**现象**：
- 前端 414 次调用中 373 次只读，占 token 的 90%。05:16 后 179 次调用、10.0M，零写入。
- 读放大：

| 被读对象 | 大小 | 被读了多少 | 次数 |
| --- | --- | --- | --- |
| `pages.css` | 24.5K 字符 | 140K 字符（通过 sed/awk/grep） | 66 次 |
| `ui.js` | 16K 字符 | 149K 字符 | 51 次 |
| `api.js` | 7.4K 字符 | 91K 字符 | 41 次 |
| 设计文档 | 20.2K 字符 | 187K 字符 | 9.3 倍 |
| 契约 | 13.2K 字符 | 84K 字符 | — |

**根因**（都是通用机制，不是前端特例）：

1. **写过的东西自己看不见**。L2 把写文件调用的大参数换成占位符。台账只记路径和 sha，不记结构。模型要知道 `ui.js` 导出了什么、`combobox()` 返回什么、`.editor-toolbar` 叫什么，只能回读。实现越往后，“自己的代码”占工作集越大。前端到后台页面这一步时，工作集包括：
   - 11 个模块的签名（约 2,300 行 JS）；
   - 3,150 行 CSS 里的类名；
   - 设计 §6.1–6.3 和契约后台接口。
   
   远远超过原文层 30K。
2. **L3 段摘要记录“做过什么”而不是“得到什么”**。例如：
   - “Read router, format, api (chunks), types, session libs to map state flow… No files modified”
   - “Learned: toast/dialog roots exist in HTML; CSS uses BEM-like naming”
   
   签名、类名、字段这些下一步真正要用的事实全没进摘要。所以一段被摘要掉，对应的读取就得重做。
3. **模型不写计划**。前端 checkpoint 里 28 条 AI 消息正文全是空的，只有工具调用；qwen 的推理内容不进历史。“下一步写 admin.js，需要 X、Y、Z”这种意图，每轮都要从头推。折叠一次，意图就丢一次。`collaboration_journal` 一次都没用过（notes 为空）。
4. **读循环处理适得其反**。
   - 12 轮时的提醒是软提示，被无视。
   - 24 轮时的“干净交接”（`worker.py:191-194`）把历史换成台账加最近原文。模型读个不停，恰恰是因为工作集装不下；交接把刚读进来的又扔掉，下一轮只能再读。
   - 这条规则在 Blog2 方案里假设“读循环是因为折叠窗口太小”，但这次窗口已经放大，循环的原因换成了“工作集本身太大、而且没有结构化索引”。

#### A4. 睡眠或挂起让所有租约过期，后端丢失未合并的工作（P0）

- **证据**：`pmset -g log`：13:38:53 `Entering Sleep state due to 'Idle Sleep'`，13:56:10 `DarkWake`。期间没有任何模型调用和工具调用，Leader 也停了。
- 平台运行任务时**没有持有阻止空闲睡眠的电源断言**（类似 `caffeinate -i`）。系统里只有 coreaudiod 和 powerd 的断言，而且在 13:38:48 显示器关闭时释放了。
- 租约 `lease_until = time.time() + 60`，按墙上时钟算。唤醒后 `recover_requests` 或调度看到租约已过，把两个任务都标成 `interrupted_reason='execution lease expired'` 重新排队。
- **后端**：因为 A1 留下的 `workspace_published=True`，attempt 2 拿到**新的工作区**（从根目录复制），模式是 `fresh`。快照里的 `check_contract.py`、根目录 `migrate.py`、`.task-scratch/*` 全部不见了。它花 54 分钟重写自检脚本，重新逐条对照契约。
- **前端**：attempt 2 续接同一线程。旧实例在睡眠前发出的模型调用 06:01:03 才返回（338 秒），工具被跳过。05:56–06:01 有两个图实例共用一条 checkpoint 线程，存在写分叉的风险。
- 不睡眠也会触发：任何超过 60 秒的事件循环阻塞，都会让所有在跑的任务被重排。

#### A5. 等待用户审批时，任务静默卡住（P1）

- 05:33:21 后端执行 `cat $WDRUNGE_DATA_DIR/blog-admin-credentials.json`。AI 审核判为“读敏感凭据、与任务无关”，转用户审批。后端在工具调用里一直等到过期，Leader 和界面都没有显式提示“某任务在等审批”。
- 审核前后不一致：04:5x 时一条 `python -c` 读取同一文件**并把密码打印到标准输出**的命令被放行了。凭据也是 Leader 要求后端读取并私发的。
- 这条命令本身也有问题：没经过 shell，`$WDRUNGE_DATA_DIR` 根本不会展开，批了也会失败。

#### A6. 递归上限是硬失败，续接后照旧（P1）

- 前端 05:22:39 因为 `GraphRecursionError: Recursion limit of 1000` 失败。
- 1000 步大约是 250 轮“准备 → 模型 → 工具 → 确认”。它是兜底，不是调度手段：
  - 失败后 Leader 只能重排，续接同一上下文，循环原样继续；
  - 失败记录是一段 LangChain 异常文本，“Resume after an interruption (the previous attempt failed: Recursion limit…)”被原样塞进任务输入，在上下文里叠了两份。

#### A7. 段摘要无限累积，续接交接重复叠加（P1）

前端最终 checkpoint 约 80K 估算 token（按字节/2）：

| 构成 | 条数 | 占比 |
| --- | --- | --- |
| 原文工具结果 | 24 条 | 41% |
| **段摘要** | **49 条** | **26%** |
| **任务输入和交接** | **7 条** | **17%** |
| 系统提示 | — | 7% |

- 交接这 17% 里有三份“Assigned task: Resume…”，每份都带完整 journal，约 4.6K 字符。
- 后端第一轮：段摘要 63 条，占 39%。
- 上一份报告 10.4 已经预计到“段摘要累计后下限缓慢上升”，这次确认了，而且比重放时更高。

### B. 规则与提示词

#### B1. 前端的实现策略放大了工作集

“原生 ES Module、无构建、自造 `h()` 和路由、先写完所有页面的 CSS，再写 JS 对齐类名”。这条路线下，每写一个页面都要和几千行 CSS 精确对齐类名。

提示词里没有引导：
- **按纵向切片推进**：一个页面的 JS 加它自己的样式一起写，写完就跑起来看；
- **优先用常见框架和脚手架**：减少自造基础设施。

#### B2. 没有“先跑起来”的硬性节点

前端三个小时里：
- 从没启动过 `server.mjs`；
- 从没 `node --check`；
- 从没打开过页面。

所以 `public.js` 的语法错误、缺失的 `main.js` 一直没被发现。worker 提示词只说“交付前自测”，没要求“每写完一个可运行单元就运行一次”。

#### B3. 需求文档把“内容生产”写成了验收条件

需求 §7.5 规定了示例数据的篇数、语言、表格引用列表、分类标签和状态组合。这本来是为了**能验收**分页、高亮和可见性。但没说“用代码生成短内容即可”，后端就写成了 14 篇真文章。Leader 又叮嘱“不要削减种子数据”。

产品和 Leader 提示词应说明：示例数据的目的是覆盖验收路径，用脚本生成最短内容，不写成真实文章。

#### B4. Leader 基于平台的错误信息做了错误决策

05:25:43 的“迁移修复”指令完全是 A2 的错误事件误导出来的。Leader 当时可以用 `collaboration_inspect_request` 或日志核实，但事件里没有可核实的东西（无输出、无原因）。

修 A2 后，事件里应该带上原因和日志指针。

## 9. 其他影响效率的因素

  - Leader 还要求通过协作消息私发；
  - `execution_permissions`、`project_resources` 里连接服务的口令也是明文保存。
- **遥测**：`tool_calls.arguments` 截断到 8,000 字符，大文件写入的路径都解析不出来（时间线里 `path=None` 的那几条）。
