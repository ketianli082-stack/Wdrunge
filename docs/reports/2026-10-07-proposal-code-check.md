# 项目说明文档与代码核对报告

核对对象：《Wdrunge：面向 Web 开发的多智能体协作系统》中的技术方法和其他描述。
核对依据：`context-desk` 分支当前代码（2026-10-07）。

结论：大部分描述与代码一致。有四处说得过头或与实现不符，实验评估部分依赖的功能目前还不存在。

## 一、与代码一致的部分

- **六个角色**：Leader、产品、后端、前端、美工、测试，在 `backend/app/agents/team.py` 中创建，每个角色的工具集不同。
- **契约就绪后放行前端**：任务可以等待某份文档或某个服务（`needs`）。作者以 `ready=true` 发布该文档，或产出它的任务交付后，等待即结束（`planning.document_released`）。前端任务如果依赖后端的实现任务，平台会拒绝，除非给出理由（`planning.serial_dependency`）。
- **结构化交接与共享项目状态**：需求、契约、报告都是带版本的共享文档；任务、目标、验收标准、证据和每个任务的工作记录都存在数据库里。
- **失败后返工**：Leader 可以把任务从 `review` 转回 `queued`，成员带着验收意见在自己原来的上下文里继续。
- **项目事实独立于对话历史保存**：台账记录文件、文档版本、进程与端口、命令退出码、浏览器验证结果和未解决的失败，压缩后不会丢。
- **隔离执行**：每个任务在项目目录之外有自己的文件快照，交付时用三方合并写回项目，并检测冲突。命令在系统沙箱中运行（macOS 用 Seatbelt，Linux 用 Bubblewrap），只能写本任务的快照。

## 二、需要修改的部分

### 1. 验证说得过头（第 37 行）

原文说只有完成验证后任务才会被接受。代码里，验证不是平台自动执行的关卡：

- 构建、测试、浏览器验证由成员自己用工具完成。
- 提交时平台检查：
  - 声明的文件和文档存在；
  - 声明的服务正在运行；
  - 任务依据的文档在它读过的章节里没有变化。
- 其他提交检查（`collaboration/delivery_checks.py`）只给出提示，不阻止交付。
- `complete_task` 要求每条验收标准对应一条证据文字。平台只检查证据是否齐全，不检查是否属实（`collaboration/goals.py` 的 `check_evidence`），最终由 Leader 判断。

建议改写：

> 成员自行通过构建、命令、服务检查和浏览器验证取得证据；平台在提交时检查交付物存在、声明的服务正在运行、依据的文档未变；Leader 按逐条验收标准的证据验收，不满足则退回返工；最终由一个端到端测试任务做整体验证。

### 2. 按角色划分的文件权限只在 Wdrunge 自身仓库生效（第 9 行）

`ROLE_CONFIG` 确实为每个角色规定了可写目录，但 `backend/app/agents/tools/_workspace.py` 第 17 行的 `effective_roots()` 在项目不是 Wdrunge 仓库本身时，把它们换成 `"."`。在普通的用户项目里，每个角色都能写整个项目。角色之间真正的区别在工具：

- 产品和美工不能执行命令；
- 只有前端和测试有 `browser_verify`；
- 只有测试有 `run_project_check` 和 `run_service_check`。

二选一：文中改为“各角色的工具不同”，或者修改代码，让目录限制对所有项目生效。

### 3. 调度描述不够准确（第 31 行）

原文说由 Leader 根据项目状态决定任务何时执行，且不采用固定流程。实际情况：

- **流程是固定的**：新功能先由产品写需求文档，Leader 验收后，用一次 `create_tasks` 调用建完其余全部任务。这个顺序由平台在 `plan_task` 中强制检查。
- **启动任务的是调度器，不是 Leader**：任务图建好后，调度器在任务的依赖或 `needs` 满足时立即启动它。Leader 只在有任务交付、阻塞或有人 @它时被唤醒。
- **下游在交付时开始，不等验收**：上游任务进入 `review` 后，其他角色的下游任务就可以开始；只有同一角色的后续任务要等上游 `completed`（`collaboration/service.py` 第 839 行）。
- **端到端测试的依赖来自提示词**：平台只保证每个目标最多一个端到端任务。“测试任务依赖全部模块任务”是 Leader 提示词要求写的，不是平台强制的。
- **并行发生在角色之间**：默认每个角色同一时间只执行一个任务（`WDRUNGE_ROLE_CONCURRENCY=1`）。

### 4. 上下文压缩部分漏掉了几个组成部分（第 35 行）

代码里是五层，另加一个“工作台”（agent 读过的文件和文档的当前内容）：

| 层 | 做什么 | 调用模型 | 代码 |
| --- | --- | --- | --- |
| L0 | 新返回的工具结果限长，并去掉重复 | 否 | `context_fold.ingest` |
| L1 | 删除冗余结果 | 否 | `context_fold.prune` / `supersession` |
| L2 | 较早的结果折叠为摘录和可重新获取的指针 | 否 | `context_fold.fold` |
| 工作台 | 保存读过的文件和文档的当前内容，每次改写历史时刷新 | 否 | `context_desk` |
| L3 | 已完成的工作段生成摘要 | 是（单段小调用） | `ContextMemory.collapse` |
| L4 | 整段历史摘要 | 是 | `ContextMemory.summarize_history` |

原文 L1～L4 的描述基本对应，有两处需要更正：

- **L4 按上下文大小触发，不按任务时长**：在 L1～L3 之后仍超过预算、供应商报上下文超限，或 agent 调用 `checkpoint_context` 时执行。摘要失败时改用平台生成的交接，不调用模型。
- **L1～L3 何时生效由缓存代价决定**：这些改动合并成一次改写，只有等待的代价超过改写的代价（考虑前缀缓存）时才提交（`ContextMemory.worth_rewriting`）。这是设计的核心，值得写一句。

### 5. 代码中 API Contract 的含义（第 31 行）

代码里的契约是每个模块一份的 Markdown 文档 `docs/backend/api-<module>.md`，作为共享文档发布。`refresh_api_contract` 只在项目带有 Wdrunge 自己的 `backend/scripts/export_openapi.py` 时才能导出 OpenAPI。如果文中暗示的是 OpenAPI 或 schema 级别的契约，应改为“文档形式的接口契约”。

## 三、实验评估部分（第 59～79 行）

- **实验模式都还不存在**：代码里没有单 Agent 模式、没有“无协调机制的多 Agent”模式，也没有消融实验需要的开关（并行调度、结构化交接、context checkpoint、测试 Agent）。也没有任务 benchmark；`backend/scripts/benchmark_*` 只测后端自身开销。作为计划可以，但这些模式需要另行实现。
- **checkpoint 消融意义不大**：`checkpoint_context` 只是 agent 可选调用的工具。去掉上下文压缩（L1～L4 和工作台）作为消融项更有意义。
- **成本和上下文指标已有数据来源**：
  - `agent_usage`：每次模型调用的 token，含缓存命中和推理 token，可按角色、任务汇总；
  - `context_compactions`：压缩次数及压缩前后的大小；
  - `tool_calls`：全部工具调用；
  - 任务工作记录：执行尝试和失败。
